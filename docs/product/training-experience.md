# 产品方案 — 训练体验与交互式训练方案

> 版本: v1.58 · 日期: 2026-08-14
> 状态: 训练作为报告结论的处方与执行模块，方案主线与本轮精简规则已完成核心运行时收敛。训练规划必须从共享 `TrainingDayFact` 生成带版本 `ConsumerProjection` 的强合同已确认，存量 `summary_version` 兼容与工程收敛待完成；完整自动衔接、Provider 真实验收、严格 journal 级跨文件原子恢复和完整阶段状态机仍为 Proposed。未引入伤病管理、Safety Hold 生命周期、暂停态、课程编辑器、新设置页或规则版完整方案。
> 配套技术设计: [training-system.md](../design/training-system.md)

## 1. 背景与问题

当前运动大纲主要以 AI 记忆和日报摘要存在。用户只能感知训练阶段、剩余周数、计划周跑量等少量信息，无法持续看到今天做什么、本周如何推进、计划为何变化，也没有“反馈现实约束—查看调整差异—确认生效”的协作闭环。

训练能力需要从隐藏的文档型记忆升级为报告结论可落地的处方与执行体验：用户先在报告理解发生了什么和下一步建议，再在训练中查看今日安排、反馈现实变化并确认调整。

现有活动记录还缺少稳定的训练内容识别：第三方类型不能可靠区分有氧跑、节奏跑和间歇跑，爬升也没有形成独立的坡跑、越野或山地证据。历史日报又只覆盖用户主动生成的日期，不能作为完整训练史。系统需要直接基于原始活动、分段、个人能力和当下恢复状态解释“这堂课实际练了什么”，再把结论用于日报、执行判断和后续安排。

训练方案目前还隐含假设“用户确认当天立即从固定第 1 周开始，并按日历逐周推进”。现实中用户可能在周中、周末、大负荷训练后、旅行期间或草稿生成多日后启用；近期跑量也可能因为出差、伤病、数据缺失或主动恢复暂时偏离其长期水平。系统必须区分当前状态、当前可持续能力和历史已证明能力，生成一个安全的推荐开始安排，由用户确认或修改日期；生效后再依据每周适应结果决定调整、推进、保持、降载或重规划。

## 2. 产品目标

训练模块持续回答五个执行问题：

1. 我今天练什么？
2. 为什么这样安排？
3. 我这周和长期目标进展如何？
4. 如果现实情况变化，计划如何安全调整？
5. 我刚完成的训练属于什么内容，会怎样影响接下来的安排？
6. 我应该何时、以什么速度进入和推进这份方案？
7. 我还缺哪些同步数据，补齐后会影响日报、能力判断或下周推进吗？

目标闭环：

```text
运动记录/恢复/反馈 → 报告复盘与目标进程 → 下一周/下一阶段建议
                                                        ↓
                                     训练方案草稿 → 启用预览 → 用户确认
                                             ↓
                               本周剩余安排 / 正式周计划
                                             ↓
                                  运动数据 + 主观反馈
                                             ↓
                                      每周进程决策
                          ↙ 正常滚动        ↘ 重大调整提案
                                               ↓
                                           用户确认
```

## 3. 目标用户与范围

第一阶段的专业能力重点明确为 **“目标赛事备赛教练”**。优先服务已经选定目标赛事、目标距离和目标日期，并希望围绕成绩或完赛目标持续训练的跑者。训练方案以目标赛事为主轴，覆盖运动者了解、目标可行性、完整周期、每日执行、自然周复盘、方案级重规划、赛前策略和赛后复盘。

目标赛事必须明确目标意图：`completion` 以安全完赛为首要结果，`performance` 以目标成绩或可验证突破为首要结果。两类目标共享赛事、距离和日期，但报告的目标进程判断、训练刺激选择、风险表达和阶段结束验收标准不同；不能仅用“是否填写目标成绩”隐式推断目标类型。

第一阶段的完整体验必须形成以下报告主导闭环：

```text
了解运动者 → 判断目标可行性 → 制定备赛方案 → 训练前说明
→ 训练后分析 → 每周复盘 → 局部调整或方案级重规划
→ 比赛策略 → 赛后复盘
```

产品验收不以“能够生成一张课程表”为完成标准，而以用户能否在整个备赛周期中理解安排、执行训练、反馈现实变化并确认调整为标准。目标赛事、剩余周数、阶段目的、关键课、长距离、恢复周、减量期和比赛策略必须保持一致。

没有目标赛事时，训练板块不生成一般四周方案，也不建立另一种教练模式。用户仍可在报告查看活动解释、日报和自然周复盘，在训练页只看到已有训练事实摘要与“建立目标赛事”入口。系统不得要求用户虚构赛事，也不得把无目标建议包装成 Training Scheme。

第一版只有一条产品主线：

```text
无方案 → 建立目标赛事 → 确认可行性与约束 → 确认训练方案
→ 赛事备赛 → 目标日期结束、取消或主动结束 → 结束方案 → 无方案
```

赛事延期进入目标改期：系统先在旧方案继续生效时生成不生效的改期预览；预览成功且用户确认后，才原子更新目标、废弃旧方案并保存替代草稿。目标日期当天仍提供比赛安排；次日起自动结束当前目标与方案，已匹配赛事活动时记为 completed，否则以 `target_date_reached` 归档，不假设用户完赛。“取消开始安排”只返回方案预览；“放弃目标与方案”或执行中的“结束备赛”才同时归档 active Training Goal 与当前方案并释放主线。所有历史事实继续保留，不创建恢复过渡方案或模式转换。

## 4. 产品原则

- **行动优先**：先展示今天做什么，再展示长期理论。
- **可解释**：训练安排说明训练目的、数据依据和对后续计划的影响。
- **结果优先、理由按需**：推荐结果和用户下一步默认直接展示；推荐理由、数据依据和置信度通过“为什么这样建议”或等价入口按需展开，不在首屏连续铺陈。风险状态与必须采取的安全动作属于推荐结果，不能随理由一起隐藏。
- **用户确认**：AI 可以生成调整提案，但不能静默覆盖已生效方案。
- **实际闭环**：运动平台数据负责证明实际完成情况，用户补充主观感受和现实约束。
- **事实与推断分离**：原始活动、平台标签和 neurun 的训练解释分别保留；推断必须展示置信度和依据。
- **推理容量透明且用户公平**：周复盘、方案草稿/重规划、局部调整和赛前策略与日报共享有限的在线 AI 推理容量；同一用户同时只允许一个在线请求，重复提交立即提示请求进行中。不同用户可并发使用，超过全局容量或等待时限后提示稍后重试，不改写既有方案、报告或提案。
- **完整方案不在后台继续生成**：新建、重新生成、方案级重规划和目标改期替代草稿都在当前请求的端到端时限内完成；失败、超时、离开页面或请求中断后不自动重试、不排队等待完成、不轮询或发送完成通知。周复盘等已明确采用异步任务的其他旅程继续按各自合同处理。
- **报告主线、训练落地**：报告负责已发生事实、运动表现、恢复表现、目标进程和下一步建议；训练页负责把建议与目标转成计划、执行反馈、调整差异和用户确认，报告不得直接改写方案。
- **模块闭环、跨页引导**：报告负责观察与建议，训练负责未来安排与确认，同步负责事实补齐；跨页只传递
  日期、自然周和返回来源，不能借跳转静默写入另一个领域。
- **相对强度**：有氧、节奏等刺激按运动者当前能力判断，不使用对所有人相同的固定配速标签。
- **处方可执行**：今日训练以距离/时长、配速/心率（有事实时）、可观察体感、训练结构和完成标准表达；RPE 只作为辅助校验。
- **配速稳定校准、当天有限推进**：五级强度先映射到有证据的个人基础配速区间，再由近期表现、恢复、负荷、地形和天气形成当天执行区间；普通单日状态不能直接把基础区间推得更快，只有存在生效目标且能力与状态稳定时，才允许当天最多 1% 的只读目标推进，基础区间仍须经过新证据重新校准。
- **能力与状态优先于负荷指标**：当天执行先由近期可持续能力和近期训练表现确定基础，再由当下状态决定是否允许目标导向的小幅推进；恢复是安全修正，ACWR 只作次级风险校验，不能单独把配速放慢或否决有充分事实支持的执行。
- **强度先于凑数**：距离与时长共同出现时，系统必须先验证其隐含配速是否符合个人近期事实；不一致时不得把两者同时展示为轻松跑目标，而要收紧为单一安全目标并引导重规划。
- **周目标与课程结算分离**：Weekly Plan 的 `target_km` 与 `target_load` 是该自然周的目标值，不是阻断课程生成的硬约束。课程累计与目标不一致时，确定性 reconciler 必须先尝试在安全边界内调整课程；无法安全对齐时，以课程累计值结算并在 `adjustments` 中记录差异、原因和结算方式。仅因累计不一致不得拒绝生成周计划。
- **体系约束而非课程菜单**：课程由阶段目标、训练刺激、训练块和安全边界组合；训练体系 Skill 提供可解释原则，不能用固定课程枚举或任意模板替代运动者事实。
- **能力分层**：当前恢复、近期可持续能力和历史已证明能力分别表达；历史峰值不能直接当作当前负荷，近期下降也不能自动抹去长期基础。
- **启用可选择**：草稿确认时间、正式生效日期和首个完整训练周相互独立，系统给出建议但由用户选择。
- **适应驱动推进**：赛事日期约束终点和最小减量窗口，周表现与身体适应决定训练进程速度，不按日历机械升级。
- **安全优先**：疼痛、疾病和异常恢复进入安全流程，不以完成数量为第一目标。
- **渐进披露**：首页保持简单，训练阶段、配速体系和完整版本历史按需展开。
- **视觉连续**：训练页与“报告 / 同步 / 我的”使用同一套 `fresh / sport / dark` 主题语义和色值；训练状态可以通过文字、图标和组件层级突出，但不得以另起一套页面配色来区分模块。

## 5. 统一产品语言

| 概念 | 回答的问题 | 变化频率 |
|---|---|---|
| 训练目标 | 用户要达到什么结果？ | 很低 |
| 训练方案 | 总体如何达到目标？当前处于什么阶段？ | 每几周或发生重大约束变化时 |
| 目标改期预览 | 新日期对应的替代安排是什么，和当前方案有何差异？ | 用户提交新日期后、确认改期前 |
| 目标改期 | 何时把目标与当前方案切换到已准备好的替代草稿？ | 用户明确确认预览时 |
| 可训练安排 | 我通常每周哪几天能练、单次最长多久？ | 建立或重新生成方案时 |
| 能力档案 | 我当前能稳定承受什么，过去证明过什么水平？ | 数据或用户确认变化时重算 |
| 启用预览 | 这份方案应从何时、以什么方式开始？ | 每次草稿启用前 |
| 启用安排 | 已确认的方案何时正式成为训练依据？ | 确认、改期或取消时 |
| 本周剩余安排 | 周中启用后，到本周日之前怎么练？ | 按需，仅一次 |
| 周计划 | 这周具体练什么？ | 每周，可随状态调整 |
| 今日训练 | 今天具体做什么？ | 每天 |
| 训练处方 | 这节课如何完成、强度怎么控制、何时调整？ | 每次 Daily Workout 生成或调整后 |
| 配速校准档案 | 我的 Z1–Z5 当前分别能用什么个人配速事实表达？ | 新增可靠活动、用户确认事实或算法版本变化时 |
| 实际活动 | 用户实际完成了什么运动？ | 每次同步后 |
| 训练内容分析 | 这次活动的训练类型、地形属性和判断依据是什么？ | 活动明细或分析版本变化时 |
| 执行记录 | 实际做了什么？ | 每次训练后 |
| 训练反馈 | 用户感觉如何、遇到了什么约束？ | 随时 |
| 调整提案 | 建议修改什么，为什么？ | 按需 |
| 进程决策 | 下一周应调整、推进、保持、降载还是重规划？ | 每个完整自然周后 |
| 方案版本 | 用户确认后生效的方案快照 | 每次确认调整后 |

用户界面统一使用“训练方案”，不再将“运动大纲”“训练计划”和“今日建议”混为同一个概念。

## 6. 信息架构

### 6.1 主导航

MVP 使用四项主导航：

```text
训练 | 日报 | 同步 | 我的
```

报告成为理解状态与决定下一步的核心业务入口；训练作为报告结论的处方与执行入口。MVP 保留“报告 / 训练 / 同步 / 我的”主导航，现有日报默认入口继续兼容；同步完全自动化后可降级为状态入口。

### 6.2 训练模块

```text
训练
├── 今日怎么跑
├── 本周怎么跑 / 进度如何
└── 后面几周安排如何
    └── 训练方案（渐进披露）
        ├── 目标与约束
        ├── 阶段路线
        ├── 周结构
        ├── 能力依据与进入方式
        ├── 强度与恢复边界
        └── 当前版本与最近一次调整
```

## 7. 训练主界面

### 7.1 首屏

用户有限的注意力只优先服务三个连续决策：今天怎么跑、本周怎么跑/进度如何、后面几周安排如何。首屏先展示今日训练的完整执行处方；紧随其后以本周完成量、目标量、关键课数、长距离和训练刺激概括本周节奏与进度。

今日训练必须展示名称、距离或时长、配速或心率区间（有可靠个人事实时）、这样安排的原因、恢复是否改变原计划、训练前说明和调整今天入口。本周怎么跑/进度如何展示本周完整七日课表，默认先展示本周训练重点、关键训练刺激、关键课数量、长距离和恢复位置，以及本周计划量与实际量的并列比较；完整课表默认折叠，每项可点击展开完整处方。本周进度不计算综合完成率，只并列展示计划量与实际量及完成、部分完成、跳过、未匹配和计划外训练数量。本周比较只使用当前自然周内已同步的实际运动，不使用“最近 7 天”滚动窗口。

首页信息优先级固定为“今日怎么跑 → 本周怎么跑 / 进度如何 → 后面几周安排如何”，不得只显示阶段、剩余周数和周公里数等抽象状态。长期方案、能力参考、数据状态和已处理调整记录都属于解释或管理信息，收纳在“后面几周安排如何”内，不抢占执行任务；但待用户确认的调整仍应独立显示，不能因任何折叠层级而被隐藏。

### 7.1.1 训练前说明

训练前说明是用户即将执行课程时的快速指导，不是教练运行时或数据诊断页面。点击后应即时展示：

- 今天训练的目的和一句可执行的强度上限；
- 热身、主体和放松等不超过四条执行要点；
- 时间不足、场地受限或明显疲劳时的替代方式；
- 需要停止或改为恢复的清晰信号。

不得向用户展示内部事实字段、结构化序列化内容、Skill 名称、调用 trace、`ACWR` 数值、同步字段名或模型降级原因。系统仍可依据计划、恢复和负荷事实收紧强度或给出降级建议，但必须翻译为运动者能立即执行的语言，例如“近期负荷偏高，今天保持轻松；明显疲劳则改走路或休息”。训练前说明默认走本地即时规则，不等待在线 AI；在线解释能力不能阻塞用户开始训练。

### 7.2 本周怎么跑 / 进度如何

本周固定指用户本地时间的自然周（周一至周日），视图同时展示该自然周七天计划，并区分：

- 已完成、部分完成、跳过、待训练和等待匹配；
- 关键训练、恢复训练和休息日；
- 原计划与调整后的安排；
- 已完成公里数、课次和关键训练完成情况。

本周进度不计算综合完成率或依从性分数，只并列展示计划量与实际量，以及完成、部分完成、跳过、未匹配和计划外训练数量。比较只使用当前自然周内已同步的实际运动，不使用“最近 7 天”滚动窗口；跨周活动不得进入本周实际量，未来日期仍展示计划但不计入实际数据。

默认先展示本周训练重点、关键训练刺激、关键课数量、长距离和恢复位置，以及本周计划量与实际量的并列比较。完整七日课表默认折叠，每项显示课型、距离/时长和通俗强度摘要；非休息日项可点击展开完整 Training Prescription（目标、主体强度、体感、训练块、完成要求与调整边界），不让七份长处方淹没主视图。

长距离优先安排在用户可训练的周六/周日，无周末可训日才退化为最近可训日。该短期事实只用于本周排课顺序，不改上一完整自然周的周量基线。

点击某天进入该次训练详情。当前产品不提供通用聊天入口；课程解释、反馈、调整、周复盘和比赛策略分别由明确页面动作承载。

“本周怎么跑 / 进度如何”卡的操作区提供两个动作：“查看本周进度”（深链到报告页周 tab，查看完整进度检查/周复盘）与“刷新进度”（重新拉取训练首页数据并重渲染本周实际进度，不整页刷新）。刷新进度是纯本地实时计算，不触发周复盘生成或在线 AI。卡片底部展示数据状态行：进度统计至同步覆盖截止日、已覆盖天数/应覆盖天数；存在未同步日期时切换为警示样式并引导“先同步数据再刷新进度”。周进度数据来自当前自然周内已同步的实际运动，同步完成后需用户点击刷新（或重新进入页面）才会纳入新事实，系统不得静默重算。

周进度数字并列展示两套口径，不得混用：

- **计划执行**：“完成 X 次 / 已跑 X km”只统计完全完成（`completed`）的计划课及其实际距离；部分完成课、跳过、未匹配和计划外训练不计入。本周尚无完全完成的计划课时，收敛“完成 / 已跑”两个数字（不显示 `完成 0 次 / 已跑 0 km`），避免被误解为“没练”；此时卡片只展示目标与实际事实。
- **实际事实**：“实际 X 次 / 跑步 X km”统计周内全部已同步活动（含计划外训练与部分完成课），口径与报告页周进度 `actual_summary` 完全一致，以 accent 色标识区分。

两套口径的差异（计划外加跑、部分完成课）因此一目了然，不需要用户在两页之间对照猜数字。

### 7.3 后面几周安排如何

采用与草稿预览一致的渐进披露，默认展示阶段名称、目的与周数，以及按启用日期计算的可视化计划时间线和百分比；该时间线只能表达“计划走到哪里”，本周剩余安排不计入阶段进度，不能声称用户已经适应或自动推进。后续每周默认显示周跑量、关键课和训练目的摘要，用户可按需展开完整逐日课程。展开只改变当前页面显示，不生成新内容、不保存偏好，也不允许编辑。

- 目标赛事、距离、目标成绩和目标日期；
- 后续阶段路线和周跑量趋势；
- 当前可持续能力、历史已证明能力、数据置信度和推荐起始负荷；
- 生效日期、本周剩余安排、首个完整训练周及最近一次进程决策；
- 每周基础结构、关键课和恢复边界；
- 常规每周可训练星期和统一单次最长训练时间；
- 最近一次调整及原因；
- 当前方案版本、生效日期和最近一次调整。

## 8. 核心用户流程

### 8.1 首次创建训练方案

没有当前方案时，训练页进入三步“训练方案建立向导”，不一次性展示完整配置表单，也不要求用户理解能力模型。固定顺序为：

1. **目标赛事**：读取唯一 active Training Goal；存在时直接预填，没有时快速创建。要求赛事、距离、日期和目标意图（完赛或成绩突破），成绩突破目标可填写目标成绩。若升级前历史数据中存在多个 active 目标，进入一次性冲突修复：用户保留一个，其余原子归档，完成前不得生成草稿。赛事日期必须晚于今天；目标内容只保存在 Training Goal，不在 Training Scheme 中复制为第二份可编辑信息。
2. **现实约束**：只询问常规每周可训练星期集合和一个适用于所有训练日的单次最长训练时间。不区分早晚时段，不设置逐日最长时长，也不录入特定日期例外、请假或旅行安排；方案生效后的临时变化统一通过“时间或安排变了”提交。页面不追加周跑量、历史能力、中断原因、场地、交叉训练或其他配置字段。近期能力、历史能力、恢复和数据覆盖全部由系统自动读取；周跑量由系统提出，不要求用户自行设计。
3. **方案预览与开始确认**：核心目标和现实约束通过准入后，在发起草稿请求前显示一次可跳过的“补充近期变化”轻量窗口；用户完成或明确跳过后才提交草稿。补充窗口不是第四个向导步骤、能力表单或设置页。草稿生成成功后展示目标可行性、阶段、建议周跑量、周结构、首四周和唯一推荐开始日期，主动作只有“确认该安排”。AI 只生成当前周与下一周的课程骨架；其中 `weekday` 只表示相对星期槽位，不是最终用户展示日期。确定性排期层根据推荐开始日期把当前周与下一周投影为具体 `date`，候选读模型仍提供四周安排。候选首周默认展开完整逐日课程；第二至第四周默认只显示周跑量、关键课和训练目的摘要，用户可按需展开完整逐日课程。展开只改变当前页面显示，不生成新内容、不保存偏好，也不允许编辑。能力摘要、事实截止时间、不确定性和安全边界折叠在“为什么这样安排”且只读；用户只能返回修改目标、可训练日或单次最长时间，或在预览修改开始日期，随后重新计算同一 `plan_id` 的草稿和启用预览。

#### 草稿生成前补充信息窗口（轻量）

该窗口只收集本次草稿生成所需的可选用户上下文，不替代 `TrainingDayFact`、目标赛事、可训练日、单次最长时间或安全反馈。窗口在核心事实准入通过后、草稿请求提交前出现一次，用户必须明确选择“提交并生成”或“跳过并生成”；关闭页面、返回上一步或不操作不能隐式保存或阻塞既有草稿流程。

最小字段只有一个：

- **近期变化补充** `additional_context`：可选短文本，最多 280 个 Unicode 字符；只描述会影响近期进入方式或安排取舍的现实变化（例如旅行、工作高峰、短期训练中断或恢复安排）。空值与明确跳过等价，均记录为 `no_additional_context`，不得解释为用户拒绝生成。

输入不承载长期能力、周跑量、目标成绩、逐日时段、请假日历或疾病诊断；疼痛/伤病应从既有“疼痛或不适”安全入口提交。页面提示用户不要输入姓名、联系方式、地址、账号、密钥或详细医疗记录。超过长度、包含明显个人识别信息或无法通过安全过滤时，显示具体清空/修改提示；核心草稿准入已经通过时，用户清空后仍可按无补充信息路径继续。

补充信息遵循现有用户隔离、传输与存储保护；日志、埋点和错误提示只记录状态、长度、分类和脱敏原因，不记录原文、完整 prompt 或上游响应正文。

保存和清空规则固定为：

1. 用户点击“提交并生成”后，服务端才创建本次 `request_id` 关联的短期上下文快照，并冻结到该草稿任务；输入过程中只保留在当前页面内存，不做自动保存、跨设备同步或个人资料写入。
2. 任务终态（成功、失败、用户离开导致的中断或过期）后立即清除原始短文本；最多保留 24 小时的加密任务审计元数据（`request_id`、状态、字符数、校验结果、脱敏原因和是否采用），不在报告、训练记忆、Training Goal、Training Scheme 或方案历史中保存原文。
3. 成功草稿只保留可解释的规范化结果或 `supplement_applied` 状态，不要求用户界面回显原文；跳过/空值保留 `no_additional_context`，无效输入保留 `invalid`，存储或读取异常保留 `supplement_unavailable`。
4. 用户在提交前点击清空或返回时立即丢弃当前页面内容；任务运行期间不能编辑或追加文本。若需补充，必须等待任务终态后重新打开窗口并发起一次新的草稿请求。

草稿 DAG 的每个 AI 阶段都可读取同一独立 `user_supplement` 区块：确定性事实、目标和现实约束仍是主输入，补充文本标记为“用户自述、未验证、仅供取舍参考”。模型不得用它覆盖同步事实、硬性目标或安全底线；若与事实冲突，必须在审阅依据中标明不确定性，不能静默改写计划。`no_additional_context`、`invalid` 或 `supplement_unavailable` 时明确传递“无可用补充信息”，不增加额外阶段，也不因补充信息失败阻断核心草稿生成。

该窗口沿用现有草稿预览、任务卡和“为什么这样安排”折叠区，不新增设置入口、补充信息历史、聊天线程、复杂问卷、偏好记忆或第二次确认。用户只看到输入、字数提示、提交/跳过/清空动作及最终是否采用的简短状态。

#### 草稿预览的信息层级

草稿预览必须同时回答“为什么这样安排、现在从哪里开始、近期怎么执行、后面怎么发展”，但默认只展开影响确认决定的信息，不把内部证据平铺在首屏。固定顺序为：

1. **方案结论**：目标名称、方案状态、目标可行性、首周建议跑量和训练日数；用一段短文说明当前能力、近期状态、目标拔高、恢复和 ACWR 修正之间的关系。不得展示 Skill 名称、内部字段、调用 trace 或 ACWR 数值。
2. **当前切入点**：明确显示建议起始阶段、阶段目的、是否跳过基础阶段、是否保留适应周、推荐依据和置信度。`advance` 只表达“建议从更高阶段切入”，不能在用户确认前自动改变生效方案。
3. **近期执行安排**：以**阶段→周→课表三层下钻**展示。最上层是大阶段（如基础期/专项期/高峰期/减量期，含周数），点击后展示该阶段内每周概要（第 x 周 · 日期范围 · 跑量 · 重点 · 恢复周标记）；点击每周卡片，有详细课表（当前阶段前两周）时以**日历式模块**展示：周一至周日各占一格并标注日期，质量课（间歇/变速/节奏/LSD/阈值/比赛配速等）在格子上显示课型文案标志 + 距离，普通跑课只显示距离，休息日显示休息；无课表的周（第 3-4 周及后续阶段）明确提示“根据前几周执行情况、恢复状态和赛事临近度继续安排”。点击日历格子后，**课程细则模块**展示该课完整处方：配速区间（`pace_targets` 或体感降级）、逐段结构、完成标准和安全调整边界；展开不触发 AI 或写入。桌面端周课表与细则左右双栏，细则区固定可见；移动端课表格子保持可点按尺寸，窄屏自动切换为逐日列表。AI 只负责相对星期、课程间隔和训练逻辑，不能自行编造具体日期。课程骨架由 AI 标注**配速意图**（`pace_intent`，如轻松跑、长距离、马拉松配速 M、阈值、间歇、重复跑、节奏、恢复、比赛配速），确定性层按个人配速校准回填每堂课的**建议配速区间**（`pace_targets`：状态、Z 区、区间、展示文本、依据或体感降级）并持久化到草稿 JSON；草稿预览的课程卡片直接展示建议配速区间（有个人事实时）或可对话体感，不要求展开折叠才可见。

排课还要与最近两个已结束自然日衔接：长跑（≥20km）或质量课后的次日不安排强度；长距离优先安排在用户可训练的周六/周日，无周末可训日才退化为最近可训日。该短期事实只用于排课顺序，不改上一完整自然周的周量基线。
4. **后续周期**：首四周以每周跑量、是否恢复周和训练重点做摘要；完整周期以阶段名称、持续周数、阶段目的和负荷趋势做摘要，不默认展开每天课程。

“为什么这样安排”作为统一折叠入口，收纳数据依据、事实截止时间、能力样本、系统规范化调整、信息缺口、不确定性和低优先级审阅证据。安全提示、需要用户确认的风险和当前切入阶段不能隐藏在折叠区。展开或收起不触发重新生成、网络请求、写入或方案变化。预览不提供课程编辑器；用户只能修改目标或现实约束后重新生成完整草稿。

安全规范化调整按“安排变化 / 技术性对齐”分级展示，不得混排平铺：

- **安排变化（直接展示）**：改变用户可感知训练安排的条目——课程被改为恢复跑（“08-12 原「节奏跑」改为衔接恢复跑”）、定时跑换算距离、阶段周数规范化等；
- **技术性对齐（计数合并，不逐条平铺）**：周目标/负荷的算术自洽处理——逐周“课程累计跑量已对齐周规划目标”“负荷已按课程累计负荷结算”、完成标准补齐、后两周骨架延展等，内部处理不影响训练安排；
- **全为技术性对齐时**：收敛为一句“方案已通过确定性安全校验，仅技术性对齐，训练安排未变”；
- **分类约定**：技术性文案统一含“对齐 / 结算 / 补齐 / 延展 / 骨架”关键词，新增规范化规则时遵守，避免重新混排。

活动覆盖不足必须明确显示“历史数据不足”，不得把空数据解释为零训练量；已有活动和历史兼容能力事实继续只读使用。只要赛事、距离、日期、目标意图、至少一个可训练星期和统一单次最长时间完整，历史活动或能力证据不足也必须生成一份低置信度、保守起步的唯一方案，不增加补充数据审批或能力信息表单；草稿请求前的可选短文本窗口只用于补充近期变化，不改变这一准入规则。只有缺少上述必要输入时才阻止生成并提示补充；可选目标成绩缺失不阻止 `completion` 目标生成。只有用户在第三步确认开始日期后才形成第一个 scheduled/active 版本。

确认前的修改遵循以下规则：

- 修改目标时直接更新或重新选择共享 Training Goal；Training Scheme 只刷新 `goal_id` 和目标快照，不产生第二份目标信息；
- 修改现实约束时更新原草稿并重新生成周结构，保留同一个 `plan_id`，不得堆积多份无法辨认的草稿；
- 提交本次补充信息只影响当前草稿请求的输入快照，不更新 Training Goal、长期现实约束或能力档案；若用户重新提交补充信息，必须等待前一次任务终态并创建新的 `request_id`，不能在任务中追加或覆盖。
- 方案预览不提供周跑量、历史能力、中断原因、训练日期、课程类型、训练步骤或单课内容的直接编辑；用户只能修改目标、可训练日、单次最长时间或开始日期，系统据此重新生成并完整校验同一份唯一草稿；
- 新输入提交后旧草稿立即退出当前读模型，不能再展示或确认；重新生成成功后写入同一 `plan_id` 的唯一新草稿，不保留旧草稿正文、版本列表、差异视图、撤销或恢复入口；生成失败时只显示失败与重试，不回退展示旧草稿，也不产生半份新草稿；
- 只有 `draft` 状态可以修改上述输入；已生效方案必须通过调整提案。只影响今天或当前周时形成局部安排，改变未来负荷、阶段或目标路线时才产生新方案版本，任何范围都不能被确认页静默改写。

Training Goal 是目标信息的唯一真相源，一份 Training Scheme 只引用一个目标，并保存用户确认方案时的目标快照用于历史解释。**训练**是 Training Goal 的唯一交互入口：用户只在没有当前方案的建立向导内选择、新建或编辑目标；“我的”只维护账户、数据源、身体资料和训练偏好，不展示目标列表或目标增删改操作。草稿、已排期或执行中任一状态都不得并行创建第二个目标或方案。已有当前方案时，用户提交新日期只生成 Goal Rescheduling Preview，当前目标、今日训练和执行评价保持不变；预览成功且用户确认后，系统才一次性更新同一目标、将旧方案转为历史并保存替代草稿。替代草稿再次确认启用前不得提供今日训练或执行评价。

新流程同一时间最多一个 `active` Training Goal；`completed` 或 `archived` 目标只进入历史，不在建立向导中自动预选。用户在草稿/启用预览明确点击“放弃目标与方案”，或在 active 方案点击“结束备赛”并确认后，系统原子归档当前方案与对应 active goal，保留目标快照、方案版本、排期、执行和报告历史，并释放唯一主线。只归档方案、却留下会被下次自动选中的 active goal 属于非法半完成状态。

系统自动读取近期和历史跑量、训练频率、长距离、关键课、成绩与恢复状态，只向用户询问目标、可训练日和单次最长时间；草稿请求前另提供一次可选的 280 字以内近期变化补充，不将其当作能力字段或长期偏好。未确认的草稿不得作为今日训练依据；草稿生成后发生新训练或系统能力画像变化时，启用预览必须标明依据变化并建议刷新，不要求用户补填能力信息。

验收时，用户必须能在最终确认页返回目标或现实约束，并修改开始日期；修改后看到重新计算的草稿，草稿标识保持不变、今日训练不受影响，直到用户显式点击“确认并启用”。页面不存在独立“能力基础”编辑入口。

最终确认页只负责查看、返回修改输入、修改开始日期和确认，不建设课程编辑器。即使用户只想改变一节课，也必须先修改对应现实约束并重新生成完整候选，不能在 AI 候选上做局部手工覆盖。

#### 专业方案制定能力（已实现）

原按周跑量比例生成模板和现有 `deterministic_fallback` 完整方案属于待移除兼容实现，不再是目标草稿来源。目标草稿由“结构化运动事实 + 方案制定 Skill + 同次 AI 审阅 + 最小确定性执行校验”产生，并至少回答：

- 目标在剩余时间和现实约束下是否可行，判断依据、置信度和主要缺口是什么；
- 当前能力画像如何，包括近期跑量、频率、长距离、关键课、近期成绩、恢复趋势、训练连续性和伤病关注；
- 完整训练周期如何划分，每个阶段持续几周、训练目的、进入条件和退出条件是什么；
- 跑量、关键课、长距离、恢复周和赛前减量如何演进，而不只是展示第一周固定比例；
- 当前周和下一周具体做什么，以及后续首四周由规则延展出的课程目的、强度依据、替代方案和调整触发条件是什么；预览默认展开候选首周，第二至第四周先显示摘要并允许按需展开完整内容；
- 使用了哪些事实、哪些事实缺失、做了哪些假设，用户应修改目标、补充数据，或在生成前提供一次可选的近期变化上下文；该上下文不是事实来源。

#### 草稿 AI 事实载荷（已确认）

训练草稿的在线 AI 只接收形成方案决策所需的最小事实集，不把完整活动历史、完整单日事实对象或任务运行诊断一起发送。载荷压缩只能删除与训练决策无关的重复字段和运行信息，不能以减少输入为由删除会改变起步负荷、课程衔接、恢复安排或安全判断的事实。

必须保留的决策事实包括：

- 目标赛事、目标意图、剩余时间、可训练日和单次最长时间等已冻结的目标与现实约束；
- 当前能力、上一完整自然周的实际周量基线，以及当前 AI 阶段已经确定、供后续排课使用的建议周量目标；基线与目标语义分开，不把目标值写成已完成事实；
- 最近两个已结束自然日的训练摘要，至少能识别是否存在长距离、质量课、休息或未知覆盖，用于避免在大负荷训练后紧接强度课；
- 最近两个已结束自然日的每条跑步会话必须引用与日报、周复盘相同的
  `SessionSummaryFacts.fact_version` 和 `TrainingDayFact.fact_version`。compact
  投影必须保留可用的活动距离、平均配速、可靠有序分段、心率、步频和步幅；任一项不可用时保留
  `field/reason/affects` 形式的显式 gap。只有经距离比例门禁确认的公里 lap 才能表达为“每公里分段”；
  普通平台 lap 仍称“分段”。这些事实用于课程衔接、近期表现和强度证据，不要求 AI 接收原始 Hz 点。
- 事实快照版本和截止时间，以及截至该时间的恢复状态、数据覆盖、缺口和置信度；恢复未知时必须保留“未知”，不能按恢复正常处理；
- 疼痛、疾病、异常恢复、单次上限、关键课间隔、周量增长和其他会限制课程生成的安全边界；
- 本次经安全过滤的 `additional_context` 及其未验证属性；没有可用补充信息时只传递业务状态，不传递处理过程。

训练规划载荷必须是 `consumer=training_planning` 的 `ConsumerProjection`，其
`source_fact_versions` 锁定上游单日事实，`fact_version` 锁定本次投影内容。
投影只能做字段选择、时间窗口聚合和安全脱敏，不能重算距离、配速、心率、
步频、步幅、分段可靠性或恢复状态。被投影策略排除的已知字段进入
`omitted_fields`，源头未知才进入 `gaps`；两者不得互相伪装。

不得进入训练决策载荷的运行诊断元数据包括：任务 ID、排队/执行阶段、等待时间、请求耗时、重试次数、Provider HTTP 状态、调用 trace、序列化调试字段、原始模型响应和内部 handoff 文本。它们可以留在独立的短期运行日志或审计记录中用于排障，但不能成为方案内容、AI 训练事实或模型判断依据。面向用户的失败提示继续使用脱敏后的失败阶段和可操作原因，不因载荷压缩而暴露诊断字段。

草稿压缩可以移除原始 `detail_json`、原始 1Hz 数组、完整历史逐段列表、重复 evidence、完整分位
分布和仅用于报告展示的文案；不得移除最近两日六项运动事实中的可用值，也不得把解析失败、单位未
确认、距离门禁失败或投影省略转换为空值或零值。上一完整自然周及更早窗口可以只保留周量、频次、
最长单次、训练类型、结构特点和数据质量聚合，避免把全量活动历史发送给 AI。

相同的目标、决策事实和安全边界即使伴随不同的任务运行记录，也必须形成相同语义的 AI 输入；载荷压缩前后，草稿仍须通过相同的 Schema、处方补全和安全校验。任何必需事实因压缩、读取或投影失败而不可得时，系统必须显式降低置信度或停止生成，不能静默采用空值、零值或默认正常状态。

若目标明显不可行，系统不得生成 Training Scheme Draft，也不得展示保守、平衡等多条路线。页面只显示一条 `Feasibility Recommendation`：解释不可行原因与关键证据，并给出满足安全边界、对原目标偏离最小的一项修改。赛事日期仍允许安全备赛时优先放宽可选目标成绩；只有日期本身无法形成安全周期时才建议改期。用户只可“接受建议”或“修改目标”；接受后更新同一 Training Goal，再基于新目标生成唯一草稿，不预生成并行方案。

若目标具有挑战但仍能在安全边界内形成方案，系统直接生成唯一方案预览并在其中标明主要风险、预期取舍和调整触发条件。用户仍只执行一次“确认该安排”，不增加风险弹窗、风险勾选框或第二次确认；只有 `not_recommended` 才必须先修改目标。

日报分析与方案制定在产品上是两个独立旅程：日报回答“今天实际发生了什么、身体状态如何、与当前方案有什么偏差”，方案制定回答“未来如何达到目标”。方案制定可以使用结构化活动分析和恢复结论，但不得读取日报自然语言正文作为训练事实；日报也不得在生成过程中静默创建或改写长期方案，只能建议进入调整提案流程。

训练页必须区分 AI 来源、AI 审阅结果、校验结果和推荐结论，不能把一般审阅提醒写成“AI 失败”。`generation_mode` 继续作为兼容字段，同时新增 `inference_source`、`validation_status`、`recommendation_status`、`decision_status` 和 `adjustments`；候选可携带非阻断 `review`（`status`、`items`、可选 `safety_hold`）。`review.items` 只解释周期、负荷、恢复、关键课间隔、长距离比例、配速适配和目标取舍等建议；`safety_hold` 需要用户最终确认，但不增加独立页面或第二次 AI 请求。

页面结果包括“AI 训练框架 + 近期课表”“AI 方案·已安全规范化”和不含训练内容的“AI 目标修改建议”。前两者保留可行性、能力/目标摘要、证据和风险；第三种只展示一项 Feasibility Recommendation。缺失数据可形成带缺口标记的降级草稿；模型服务失败、输出不可解析或方案存在无法机械修正的安全冲突时，不创建草稿或提案，只显示阶段化失败原因和“重新生成”；已有目标、草稿或生效方案保持原样。所有方案候选仍需用户确认后才能生效，接受目标修改建议本身不会启用方案。

补充信息本身不是方案生成准入条件：输入校验、脱敏、短期存储或 prompt 处理失败时，核心事实已经通过准入的请求必须按无补充信息路径继续；结果标记 `supplement_unavailable`，不得显示为“无可确认草稿”。只有目标、现实约束、事实覆盖或方案结构触及既有硬性边界时，才按原流程阻断草稿。

“重新生成”始终是用户动作。页面不得根据 `Retry-After`、计时器、网络恢复或重新进入页面自动再次提交；每次点击只发起一次新的阶段任务，并按失败阶段复用可用中间结果。

请求进行中显示与同步任务一致的异步任务卡：读取并校验训练事实、生成训练框架、生成当前与下一周课表、补全配速并校验安全边界四段状态；不显示百分比、模型内部思考或预计完成时间，也不提供取消按钮。任务 ID 保存于本地，刷新页面后继续轮询；成功进入唯一预览，失败显示失败阶段、原因、已完成、未完成、影响和统一“重新生成”动作。服务重启、任务过期或任务归属不再可读而返回 404 时，页面立即清除本地旧 task ID、停止轮询并提示用户重新生成，不把旧任务当作仍在运行。

草稿与草稿更新允许最多 300 秒（5 分钟）的端到端生成等待，以容纳 Provider 的长尾响应及网络收尾；连续 45 秒没有任何响应数据、非 200、响应过大或输出无效仍立即失败。页面不自动重试。

任务从提交时冻结目标、训练基础、现实约束和本次补充信息快照。任务等待或运行时，草稿表单的全部输入和提交按钮均不可编辑；任务失败后恢复编辑，任务成功后进入草稿预览。用户若要改变设置或补充上下文，只能在失败后或进入预览后重新提交，不会悄悄改变正在生成的候选。

训练方案是中文用户旅程：课程名称、阶段名称、训练目的和强度说明在训练页统一显示中文。草稿预览必须明确展示“建议从哪个阶段开始”，说明是从基础期保持还是基于当前能力建议进入更高阶段；该建议仍需用户确认，不自动改变方案阶段。每个非休息课程同时展示有可靠个人事实时的建议配速区间，否则明确显示按可对话体感执行。Provider 返回的英文课程短语只能作为内部候选事实，不能直接出现在草稿、今日训练或本周安排中；未命中的自由文本保留原文并由后续产品化词典补充，不伪造翻译。

只有方案链路中的贡献 Skill、主 Skill、结构化输出解析和确定性安全校验全部成功，草稿才可以标记为“AI Skill 专业方案”。运行时必须统一满足在线模型的结构化输出协议，不能要求每个业务 Skill 重复记忆供应商参数约束。接口失败时页面展示可操作且不包含密钥、完整请求或用户原始数据的降级原因；HTTP 状态码不能成为唯一诊断信息。

AI 负责目标可行性、阶段划分、课程骨架、训练目的、训练刺激、相对强度意图和方案自审，不负责精确小数算术或逐段步骤正文。确定性层只延展当前周/下一周骨架、补全 Workout Steps v2 并规范字段；阶段周数、容量、增长、恢复周、课程比例、配速适配和医疗/恢复取舍不再静默改写或硬失败，统一由 AI `review` 给出建议，必要时以 `safety_hold` 交给用户确认。所有结构补全写入 `adjustments` 和规划 trace，不生成第二套规则版长期方案。

### 8.2 计划启用与本周剩余安排

用户点击启用前，系统必须生成启用预览，不能把服务器当天日期直接当作用户的唯一开始选择。预览至少展示：

- 草稿生成时间、事实截止时间及生成后新增的训练或反馈；
- 当前可持续能力与历史已证明能力的差异、近期下降原因和数据置信度；
- 一个推荐开始日期、首周负荷、第一堂关键课和长距离日期；
- 从生效日到首个完整自然周的衔接安排；
- 该安排对阶段周数、负荷风险和目标可行性的影响，以及次要的“修改开始日期”入口。

启用页只有一条主路径：“确认该安排”。用户修改开始日期后，系统必须重新计算并返回一个新的唯一安排，不并列展示多个进入策略或要求用户自行判断更激进的起始负荷。

启用时间使用四个不同语义：`created_at` 是草稿生成时间，`confirmed_at` 是用户确认时间，
`effective_from` 是用户选择的正式生效日期，`first_full_week_start` 是首个完整自然周开始日。不得再用单一
“激活日期”同时承担这四个含义。

当前唯一草稿通过启用确认后才形成 `scheduled` 启用安排：训练页展示“已确认，将于 D 开始”、倒计时、推荐起始负荷，以及“修改开始日期”“取消开始安排”入口，但在 D 之前不生成今日训练、不参与执行评价，也不占用阶段周。修改日期时重新生成启用预览；取消开始安排则撤销 schedule，保留目标、方案内容和历史确认记录，并回到同一方案的草稿/启用预览。它继续占用唯一方案主线，不等于归档或放弃方案，也不伪装成已经执行过的方案版本。系统不得同时保留两份 draft、scheduled 或 active 方案。

用户可以在周中确认并立即生效，不限制必须从周一开始。当 `effective_from` 不是周一时，系统生成“本周剩余安排”：

- 只覆盖生效日至周日，考虑本周已经完成的训练和当前恢复；
- 不用剩余几天补齐完整周目标，不反向生成生效日前的课次；
- 内部可继续使用 `week_kind=bridge` 兼容字段，但用户界面只显示“本周剩余安排”；该安排不计作完整阶段周，也不单独触发调整或落后判断；
- 下一个周一进入首个完整训练周；若用户主动选择下周开始，本周只展示准备和恢复指引。

若草稿生成后新增训练、系统能力画像变化、出现疼痛/疾病反馈或草稿超过配置化新鲜度，页面先显示“方案依据已变化”，要求重新生成启用预览；系统不得静默沿用旧首周负荷。用户可以保留原草稿方向，但必须看到差异和风险。

系统内部仍可记录保守、正常或加快恢复三种计算路径，用于解释起始负荷与审计，但用户不选择也不需要理解这些内部枚举。长期停训、恢复不稳、疼痛关注或数据不足时只能计算保守安排；历史能力可靠、近期下降非伤病且恢复稳定时，可以在当前安全负荷内更快接近历史已证明区间。历史能力只决定恢复上限和观察窗口，不能直接把历史峰值写成首周目标；一次高跑量或单次好成绩也不能单独触发更快恢复。

#### 8.2.1 周目标、课程累计与确定性 reconciler

每个自然周的 `Weekly Plan` 同时保存两个不同语义的量：`target_km` 表示该周建议完成的跑步距离目标，`target_load` 表示该周建议承受的训练负荷目标。两者都是计划层目标，用于解释周节奏、比较计划与实际并作为 `review-training-plan` 的输入；它们不是每一堂课或每个训练块必须精确满足的硬约束。

课程骨架和 Workout Steps v2 补全完成后，确定性 reconciler 必须计算课程累计距离与负荷，并执行一次可审计的结算：

1. 若差异可以在既定阶段、训练刺激、恢复边界和单次上限内安全消解，reconciler 调整受影响课次的距离、时长、训练块或强度表达，并将原值、新值、差异、规则依据和受影响课次写入 `adjustments`。
2. 若不能安全消解，保留课程设计的安全结构，以课程累计值作为本周结算值，明确记录 `target_km`/`target_load` 与课程累计值的差异、原因、风险和结算方式；不得为了凑齐目标而增加关键课、压缩恢复或制造不可执行步骤。
3. 仅因 `target_km`、`target_load` 与课程累计不一致，不得阻断草稿或周计划生成，也不得创建第二套规则课程。只有字段非法、步骤不可执行或触及明确安全底线时，才按生成失败处理。

周视图并列展示目标值、课程结算值和已完成实际值；不把 reconciler 调整伪装为用户已完成，也不计算综合完成率。`adjustments` 是解释和审计记录，不代表已生效的方案变更。

### 8.3 每日查看与执行

训练前，用户可查看详情、了解训练目的，或从唯一的“调整今天”入口选择三种情况：

- **时间或安排变了**：填写剩余可用时间或受影响日期；天气、场地和日程冲突只作为原因补充，不单独占据入口。临时日期变化确认后只形成当前自然周的 Local Schedule Adjustment，不打开新设置页，不废弃目标或整份训练方案；
- **身体状态不好**：补充疲劳程度及是否还能进行低强度活动；
- **疼痛或不适**：补充最小安全信息，并立即产生当日安全指引，直接显示停止、仅低强度活动或进一步评估等行动。

疼痛反馈提交成功后，当日安全指引立即覆盖“今日训练”的可执行展示，但不改写课程、周计划或长期方案。系统可以使用 AI 解释和细化行动，确定性安全规则负责最低保护并在 AI 不可用时兜底；AI 不得把行动放宽到规则底线之外。该指引只约束反馈关联的本地日期，日期结束后不再作为新的执行指引，但作为反馈证据保留。

训练后，系统同步并匹配实际运动；用户在完成记录中补充主观体感、疼痛和完成质量，不再进入“调整今天”的课前菜单，也不提供“完成”或“部分完成”按钮。系统据活动证据自动判断完全完成、部分完成、跳过或未匹配；用户主观补充不直接改写执行状态。不能可靠归入该课的活动单独标记为计划外训练；一次普通反馈不得自动重写整个训练周期。

部分完成或跳过只记录实际结果：未完成的距离、时长、组数或训练刺激不进入补课队列，不自动移到次日，也不压缩到本周剩余课程；后续已确认安排保持原样。若累计偏离、关键课缺失或恢复风险已经实质影响本周或长期路线，系统可以生成一份待确认调整提案，但在用户确认前仍不得改变后续课表。用户也可主动从“调整今天”入口提出现实变化。

计划日结束后仍没有匹配活动时，课程保持“未匹配到记录”，即使该日平台同步覆盖已经完成也不能自动改成“跳过”。课程卡只提供“今天没练”，不提供关联活动、搜索活动或手动录入；只有用户明确选择后才记录 `skipped`。用户不处理时 `unmatched` 可以长期保留，系统不得按等待时长、周末结算或空活动列表猜测用户没有训练。

用户已选择“今天没练”后，如果 Provider 迟到同步了一条同日、与该课次高度匹配且没有竞争归属的活动，系统自动追加新的 Execution Record，将当前判断更正为完全完成或部分完成，并展示“根据迟到同步已更正”；原 skipped 确认继续保留在历史中。匹配置信度不足时保持 skipped，不展示候选或人工关联入口。两种情况都不能自动补课、改写周安排或产生调整提案。

用户在计划休息日训练，或当天已有活动匹配计划课后又出现第二条未占用活动时，系统只在剩余活动上标记“计划外训练”。第一版不把多条活动拼接成一次课程。计划外训练进入本周实际运动量和报告，但不算作未来课次完成、不抵扣训练额度，也不触发自动换课、提案或重新生成。用户认为后续安排需要变化时，主动点击“重新生成安排”；系统复用现有调整提案与确认流程，确认前课表保持不变。

日报、训练首页和教练对同一日期的计划关联必须使用同一时间语义：方案在用户确认启用后才从
`effective_from` 起生效，每次确认方案级调整形成带独立生效区间的新版本。查询日期 `D` 时，系统先找到
覆盖 `D` 的方案版本，再读取日期为 `D` 的 Weekly Plan 课次；不得把当前活跃方案的周模板反向生成到
生效前的历史周。

若 `D` 没有生效方案，训练事实仍可进入日报和后续运动者基础，但执行评价状态必须是“不适用”，而不是
“未执行”或“偏离计划”。系统同时区分：当日已有待确认草稿、已确认但尚未到开始日的 scheduled 方案、
完全没有方案。前两者可以展示“仅供参考”的方案方向或未来开始日，但不能生成达标率、漏练或偏离结论。
若存在生效方案但当天没有安排，则明确显示计划休息日；待确认草稿、scheduled 方案、无方案和计划休息日
是四个不同产品状态。

#### 8.3.1 训练处方与课程编排（Workout Steps v2 核心链路已实现）

“今日训练”不是课名、距离和单个 `RPE` 的摘要，而是一份 Training Prescription。每个非休息课至少展示：

- 训练目的和完成目标，明确距离与时长哪个是优先约束；
- 热身、主体、恢复（如有）和放松的训练块；
- 强度目标：优先显示有个人事实依据的配速或心率区间；缺少可靠事实时必须明确降级为可对话、呼吸和余量等可观察体感；RPE 可同时出现，但不作为主语言；
- 完成标准、允许的偏差和时间不足、疲劳、疼痛等调整边界；
- 本课使用的训练刺激、阶段关系和方法依据的简短解释。

当前实现已经把新生成的非休息课程升级为 Workout Steps v2。为缩短草稿响应，`draft-training-scheme` 的 Prompt 只要求目标可行性、阶段、当前周与下一周课程骨架、训练目的、刺激和强度意图；不再在 Skill 文本中重复算术约束、步骤结构或安全校验细则。解释、假设和风险使用短句，不能挤占课程骨架。AI 候选只负责周期、课程骨架、训练目的、刺激和强度意图；本地确定性层根据同一候选、个人配速校准和安全规则补全顺序步骤、重复组、工作/恢复段、分段目标、完成标准及旧客户端 `blocks` 投影。AI 可以携带完整 `training_prescription` 以兼容旧结果，但如果携带该字段，必须一次性提供完整的 Workout Steps v2；不得输出只有部分步骤的半成品处方。若模型仍返回缺少完成分类的 v2 处方，Normalizer 生成稳定的最小完成标准并记录调整，不因这个可确定修复的问题让整份草稿失败。训练页仍以同一时间轴展示每段剂量、相对强度、个人目标或体感降级；步骤缺失不再因为模型输出过长而直接失败，只有确定性层无法补全或最终执行底线失败才返回生成失败。历史 v1 方案继续按原样只读展示，不会从模糊正文反向猜测组数，也不会被静默覆盖。

逐段可执行处方必须把课程顺序展开为运动者可以照着完成的步骤。对于间歇、变速、法特莱克、重复跑或含专项配速段的长距离，至少明确：

- 热身的时长或距离、强度上限和必要准备活动；
- 主体包含几组，每组工作段跑多久或多远、恢复段跑多久或多远；
- 工作段与恢复段各自的目标强度；有可靠个人事实时展示分段配速、心率或功率区间，没有时展示可观察体感和结束余量；
- 组间如何衔接，以及恢复到什么状态可以进入下一组；
- 放松的时长或距离与强度；
- 哪些步骤和组数构成本课最低完成标准，允许多大偏差；
- 时间不足、异常疲劳、疼痛或无法维持动作质量时如何减组、降级或停止。

用户看到的结构应类似“热身 → 6 组〔快段 → 慢段〕→ 放松”的时间轴。组数和快慢段长度只是结构示意，实际处方必须由本次训练阶段、目标刺激、运动者能力、当周负荷和恢复状态共同决定，不能从固定课程模板直接复制。

AI 与确定性能力按以下边界协作：

- 方案 Skill 负责选择训练刺激、课程结构、组数、工作—恢复关系、进阶意图和解释；
- 配速校准能力负责把每个工作段或连续主体段映射到个人配速、心率或功率事实，AI 不得自行编造数值；
- 确定性规则负责校验总时长/距离、重复组算术、工作量、恢复关系、关键课间隔和伤病限制；不得用机械补全把缺失的组数或快慢段意图猜出来；
- 当在线 AI 超时或输出合同不完整时，本次长期草稿或方案级重生成失败，页面保留原状态并提示重试；规则只能为当天简单调整提供缩短、停止或已有低强度形式的替代，不能合成完整关键课或长期方案；
- 修复或重新生成不得静默覆盖生效方案；用户查看差异并确认后，当周逐段处方通过局部安排生效，跨周结构变化才随新方案版本生效。

距离和时长共同存在并不代表两个硬目标。系统先以课程总距离和总时长计算隐含平均配速，再与近期有效跑步的个人配速参照比较；轻松/恢复课若隐含配速明显快于该参照，必须标记“安排待修正”。本次界面只保留可对话的单一时长目标，原距离作为待重规划依据；不得要求用户在热身、主体或放松的任一训练块内补齐该距离，也不得静默改写已生效方案。

训练课程不从不可变的“间歇 / 节奏 / 长距离”菜单中机械挑选。编排先选择当前阶段需要的训练刺激（如有氧耐力、阈值能力、专项配速、高强度耐受或恢复），再将其组织成课程块。体系知识由 Coach Skill 以方法原则、适用条件、进阶条件和禁忌约束提供；同一训练刺激可形成间歇、节奏、变速、渐进长距离等不同处方。Skill 不得伪造个人配速或心率，也不得直接修改已生效方案。

本周进度已在“本周怎么跑 / 进度如何”中展示训练重点、关键训练刺激、关键课数量、长距离和恢复位置，以及本周计划量与实际量的并列比较。完整七日课表默认折叠，每个日项显示课型、距离/时长和通俗强度摘要。每个非休息日项提供清晰的“查看训练详情”按钮；点击后在该列表下方展开完整 Training Prescription（目标、主体强度、体感、训练块、完成要求与调整边界），不让七份长处方淹没主视图。

日报读取同一份处方，按训练块、总量和强度证据判断完全完成、部分完成、跳过、等待同步或不适用；不得仅用“当天是否跑步”代替执行判断。自然周的推进决策仍只由周复盘产生。

#### 8.3.2 AI 方法学边界与五级强度参考层

AI 只生成待确认的方案候选和解释，不直接发布课程。`draft-training-scheme` 与 `revise-training-scheme` 使用同一套可审计的五级强度模型：Z1 恢复、Z2 轻松有氧、Z3 稳态/专项耐力、Z4 阈值、Z5 间歇/高强度。等级描述的是课程**主体**的相对强度；热身、恢复段和放松可处于更低等级。其边界如下：

- 五级强度以个人阈值、临界速度和近期跑步事实校准；目标成绩、通用配速表、统一最大心率百分比和设备默认 Zone 不能单独生成个人配速或心率；
- **个人阈值心率/配速只来自档案/平台，缺失时不猜测**：优先用户已确认的阈值（心率/配速），其次平台自算乳酸阈值（Coros `lthr`/`ltsp`，同步入库后自动采用），再其次由档案最大心率推导（阈值心率 ≈ 88% 心率储备，静息心率参与 Karvonen 计算）；以上都没有但档案填过 PB 时，用 PB 推导阈值配速作为配速锚点并标记来源；全部都没有时，不得用近期训练平均心率/配速分位充当阈值——近期训练构成（大量低强度课）会拉低基准，导致同一心率被高估为“阈值贴边”。此类用户训练内容识别只输出“缺少个人阈值心率/配速，强度评估不可用”，不给出“为个人阈值心率的 X%”这类精确数字；
- 周内低强度占主体是用于检查负荷分布的原则，不把“80/20”、极化、金字塔或阈值训练任何一派当成所有跑者的固定模板；选择取决于阶段、项目、近期能力、恢复与可训练日；
- 距离、时长、训练块和主体强度等级必须相互一致；Z4/Z5 使用工作段与恢复结构，Z1/Z2 使用可观察体感和个人事实守住上限；
- 疼痛、疾病、恢复异常、数据不足或一致性校验失败时，AI 只能降级、要求补充事实或提出待确认重规划，不能通过更激进的课程“弥补”进度。

五级模型是课程编排、用户沟通和安全校验的唯一强度语言。其校准只使用个人已测阈值、临界速度、近期有效跑步和可观察体感；参考层采用五级分层实践与 Critical Speed 的个体化处方研究，同时承认不存在可直接套用给每位跑者的单一最优比例。产品把它们作为选择和否决课程的共同语言，而不是作为“AI 已证明正确”的宣传。

#### 8.3.3 个体化动态配速处方（v1 已实现）

v1 已在训练首页、每周课程详情和训练前说明中接入：系统使用最近 28 天、必要时扩展到 42 天的可信同类训练分析建立个人区间；平路连续有氧、稳态/专项、阈值主体段和带工作段时长的间歇分别校准，不足三条可比样本时不显示数字配速。当天先依据当前能力和近期表现决定基础执行，再看当下状态是否允许目标导向的小幅推进，最后用恢复和训练负荷做安全修正。结果和必要安全行动默认可见，依据在“为什么这样建议”中折叠展示。

v1 尚不使用天气事实做同场景校准，也不把单次超额完成直接固化为新的基础配速；目标导向的小幅推进只属于当天只读执行覆盖，不改变 `PaceCalibrationProfile` 或生效方案。基础能力提升仍需新增可靠证据重新校准。

五级强度提供课程的相对强度语言，配速校准档案负责把它转换为当前运动者可执行的范围。系统不得把最近若干次跑步的整体平均配速直接平移成五个 Zone，也不得因一次状态很好或很差就重写长期能力。配速事实按以下优先级使用：

1. 用户确认且仍具时效性的阈值配速、临界速度或实验室/设备测试；
2. 近期比赛、测试跑或有明确距离和全力程度的结构化成绩；
3. 最近 28–42 天经 Training Session Analysis 识别的同类课程主体段，例如轻松有氧连续段、阈值段和指定时长的间歇工作段；
4. 普通跑步的整体配速统计只用于发现异常值和守住轻松跑上限，不能单独生成 Z3–Z5 精确区间。

每个可用区间必须携带适用训练块、依据、样本数、事实截止时间和置信度。默认界面只显示训练块、推荐区间和当天需要执行的调整；依据、样本、事实截止时间和置信度收纳在“为什么这样建议”入口中，用户主动展开后查看。Z1/Z2 以宽区间或配速上限为主；Z3/Z4 给主体连续段区间；Z5 必须绑定工作段时长或距离，不能展示成适用于所有间歇的单一配速。坡地、越野、极端天气或明显恢复异常的活动不得与普通平路样本直接比较，除非目标课程具有相同条件。

“今日训练”同时保留两个层次：

- **基础处方区间**：来自版本化配速校准档案，随新增可靠活动、用户确认事实或校准策略升级而更新；
- **当天执行区间**：先参考当前可持续能力和最近 7–14 天相对 28–42 天基线的同类课程表现，再由当下状态决定是否允许目标导向的小幅推进；恢复、疼痛/疲劳反馈以及可用的地形和天气事实负责安全修正，ACWR 只作次级风险校验。高 ACWR 单独不能把区间放慢或降级，只有与恢复/表现恶化同时出现时才可进一步保守处理；任何推进不得越过有证据基础区间的合理边界。

当天执行区间是只读执行指引，不修改 Training Scheme 或 Weekly Plan。若证据表明只需改变当前周某课的训练块、距离或时长，系统必须先生成可解释的局部调整提案，用户确认后形成 Local Schedule Adjustment；若需提高长期基础配速、改变主体强度等级或后续课程结构，确认后才形成新 Scheme Version。数据不足、证据冲突、场景不可比或恢复风险较高时，页面明确显示“配速暂不作为硬目标”，继续使用对话能力、呼吸和余量等体感标准。

用户默认看到的是“训练块 + 建议区间 + 当天修正”，而不是孤立的单一配速或直接铺开的推理正文；“为什么这样建议”展开后再显示依据、样本、事实截止时间、置信度和降级原因。例如阈值课应区分热身、主体工作段和恢复段；只有主体段满足证据门槛时才展示数字区间。训练后分析使用相同区间解释执行情况，但不因一次超额完成自动提高后续课程配速。

安全相关结果不因渐进披露而弱化：疼痛、恢复异常、配速不可用或安排待修正时，默认层必须直接显示“停止 / 放慢 / 改用体感 / 等待重规划”等行动；用户展开理由后再查看触发事实和证据。展开和收起只改变展示状态，不重新生成推荐、不调用在线 AI，也不修改 Training Scheme、Weekly Plan 或任何用户数据。

### 8.4 调整今天或本周

用户提交约束后，系统返回结构化调整提案，必须包含：

- 用户反馈和使用的数据依据；
- 原安排与建议安排；
- 调整原因；
- 对本周其他训练、总量和关键课的影响；
- 风险、不确定性和安全提示。

用户只有“确认调整”和“保持原计划”两个动作。只有确认后，建议变化才会按影响范围生效：仅涉及今天或当前自然周的训练日期、时长、训练量、替代课程或休息安排时，保存一条局部安排记录，不升级长期方案版本、不废弃当前 Training Goal 或 Training Scheme；改变后续周负荷区间、阶段结构、关键课演进或目标路线时，才在同一 `plan_id` 下生成新 Scheme Version，而不是创建第二条方案主线。保持原计划不会改变当前安排，也不会建立待续的对话状态。疼痛场景中，“保持原计划”只拒绝后续日期的方案调整，不能解除当天安全指引或把原强度重新显示为可执行。

局部安排必须同时保留原课次、调整后课次、受影响日期和提案依据，并参与本周执行比较。它不能跨过当前周日、改变后续周模板或暗中累计成新的长期负荷；若建议触及这些边界，系统必须在确认前明确升级为方案级提案，不能用局部调整绕过方案版本确认。

用户发现提案所依据的事实不完整时，从同一“反馈情况”入口重新提交结构化反馈，而不是在提案中继续讨论。新反馈成功生成同一调整范围的新提案时，系统必须在一次原子操作中将旧 `pending` 提案标记为 `superseded`，并只保留新提案待用户决策；新提案生成失败时，旧提案继续有效。旧提案内容和处理记录保持不可变，不能被追加消息或原地改写。

待确认提案必须仍在训练执行区域单独可见。已确认、未采纳、已被替代或已过期的调整则归档在“后面几周安排如何”的“调整记录”中，按时间倒序分页展示调整范围、原因、处理状态，以及可空的已应用周修订号或方案版本；翻页只读取历史记录，不得改变当前方案、重新生成提案或影响报告中心的周复盘。

### 8.5 每周复盘

每周结束后从报告中心生成周复盘；训练页只携带当前自然周跳转到该入口。周复盘属于报告旅程，不属于“已有训练方案”才能解锁的训练旅程。

所有用户的周复盘都生成：

- 实际运动量、运动天数、跑步天数、时长、最长单次、运动/训练类型结构；
- 与最近四个活动覆盖完整自然周的跑量、频次和最长单次趋势对比，并标明参照样本数；
- 截至该周可用的恢复、疲劳、疼痛与用户反馈；
- 活动同步、健康事实和能力档案的数据完整度；
- 有具体数值依据的负荷变化、集中度或连续训练风险；
- 2–3 条无需先建立训练方案也能执行的下周建议。

只有当该周存在实际生效的 Training Scheme 时，才增加：

- 计划与实际完成情况；
- 主动调整、数据缺失和无法匹配造成的偏差；
- 针对该方案的下一周推进建议及理由。

基础复盘始终输出 `WeeklyActualSummary`、`WeeklyTrendSummary`、`WeeklyReviewSections` 和数据质量。`WeeklyReviewSections` 固定包含“本周概览、近期变化、恢复与风险、下周行动”，归档列表直接展示核心结论，并允许用户展开完整复盘。有方案时才附加 `PlanExecutionSummary`、`AdaptationSignal` 与方案审阅结果；`PlanExecutionSummary` 同时列出 `target_km`、`target_load`、课程结算值、实际值和各执行状态计数，不计算综合完成率。无方案不是数据不足，也不生成方案进程决策。

方案草稿采用短关键路径的分阶段 DAG，不把“只能调用一次 AI”作为产品约束。同步和确定性摘要先完成，能力摘要、当前状态和目标需求可以并行复用缓存；在线 AI 拆为“训练框架”和“近期课表”两个阶段，避免把过长事实、周期理论和逐日课程塞进一个请求。完整自然周执行复盘仍使用统一的 `review-training-plan(execution_review)`，不与草稿阶段串行耦合。

草稿阶段固定为：

```text
数据同步/覆盖门禁
  → TrainingDayFact + review-daily-training（按需并行、可缓存）
  → AthleteCapabilitySummary || AthleteCurrentState || GoalDemandModel（本地缓存/并行）
  → TrainingFramework（AI）
  → NearTermSchedule + entry_review（AI）
  → Normalizer/排期/配速/课程结算/最小 Validator
  → 唯一待确认预览
```

`TrainingFramework` 只负责能力差距、目标可行性、当前切入阶段、阶段顺序、周期长度、周量/负荷/强度/长距离原则和风险；`NearTermSchedule` 只负责当前周与下一周的确定日期、热身、主课、恢复、距离、时间、配速、心率/RPE、训练目的和执行边界，并读取框架、最近两天和现实约束。第二阶段失败时只重试第二阶段，不重新生成已缓存框架；框架失败时不展示可确认的局部课表。两阶段成功后才进入本地结构化处理。

两阶段的 AI 输入必须使用紧凑上下文：训练框架只接收目标/赛程、上一完整自然周及 4–8 周聚合能力事实、恢复摘要、目标需求、训练负荷边界和缺口；近期课表只接收框架结论、当前状态、最近两天、可训练日/时长、配速参考和负荷边界，不再重复携带完整 `PlanningFactPack`、整份恢复快照或重复的历史摘要。原始活动正文、日报自然语言和已在框架中消费的长期事实不得进入近期课表请求。紧凑输入仍须保留课程配速所需的个人参考、最近两天衔接证据和缺口说明。

缺失数据默认走降级生成而不是失败：草稿标记“已生成，部分信息缺失”，展示缺口、影响、假设、风险和补充入口；只有无法形成可执行课程、结构/日期无法修复或明确安全底线不允许执行时才返回真正失败。

错误文案按阶段差异化，但用户主操作统一为“重新生成”。系统按 `request_id`、`facts_snapshot_id`、`summary_version`、`framework_id` 和 `stage` 断点续跑，复用版本一致的中间结果，不自动重试。后台为同一次草稿生成保留关联 ID、阶段和耗时，并只记录 Prompt 组成项名称、字节数和估算 token 数、模型 token 上限、请求/响应长度与校验结果；绝不记录 Prompt 全文、活动正文、补充说明、Provider 正文或凭据。仅开发者显式设置本地 `NEURUN_AI_DEBUG_PROMPTS=true` 时，终端才打印两次草稿 AI 调用的完整 system prompt 与用户事实载荷，用于短期调试；该模式不写入数据库或页面，严禁线上开启。

工作流有两个明确阶段：

- `entry_review`：作为 `draft-training-scheme` 的同次请求约束，审阅候选方案与 `target_km`/`target_load` 的一致性、课程结构、阶段路线、负荷、恢复和目标取舍；可安全应用的阶段或首周负荷修正直接反映在最终草稿中，剩余建议以 handoff 附在草稿预览中，草稿仍不可执行。
- `execution_review`：每个完整自然周（周一至周日）的执行数据结算后执行，比较本周目标、课程结算值、实际执行、身体适应和数据完整度，形成下一周建议。

两阶段都输出且只能输出以下五种 `decision_status` 之一：

| 状态 | 含义 |
|---|---|
| `hold` | 证据不足或适应波动，保持现有阶段与负荷边界并继续观察 |
| `advance` | 适应符合预期，建议在已确认边界内准备下一周 |
| `adjust` | 需要改变当前周或后续局部安排，给出可解释的调整差异 |
| `deload` | 负荷、恢复、疼痛或疲劳风险升高，建议降载或恢复安排 |
| `replan` | 现实约束、目标可行性或连续偏离已改变方案路线，建议方案级重规划 |

`entry_review` 中已安全应用的修正属于待确认草稿内容，用户确认草稿时一并确认；未能安全应用的建议只进入 handoff，不直接改写候选，用户需要时主动重新生成。`execution_review` 的结果只是下一步候选；它必须由用户在现有周复盘/调整确认入口明确确认后才生效。确认前不得激活草稿、修改当前 Weekly Plan、改变方案版本或更新目标；用户选择保持原安排时，当前方案和后续课表保持不变，并记录未采纳原因（如有）。`advance` 也不得因自然周结束自动滚动，必须先确认后生成下一周；`adjust`、`deload` 和 `replan` 需要展示原安排、建议安排、依据、风险和影响，确认后才分别形成局部安排或新 Scheme Version。

该统一工作流复用现有训练草稿预览、周复盘和调整确认入口，不新增复杂页面、设置项、课程编辑器、聊天线程或第二次确认页面。用户展开“为什么这样建议”只改变信息展示，不触发审阅、写入或自动改方案。在线解释从执行开始最多占用 45 秒；超时或慢速响应直接保留完整确定性复盘、目标/课程结算和待用户确认的决策候选，并释放账户的 AI 任务占位。

- 训练课、关键课、长距离和强度分布的完成质量；
- 最近 4–8 周可持续能力与过去 6–24 个月已证明能力；
- 配速、心率、功率或主观强度所反映的适应趋势；
- 睡眠、HRV、静息心率、疲劳、疼痛和用户反馈；
- 活动同步、训练匹配和能力档案的数据完整度；
- 当前阶段进入/退出条件、赛事剩余时间和最小减量窗口。

周复盘必须展示数据新鲜度与同步缺口。活动覆盖未知、关键课未同步或能力档案事实晚于上次复盘时，`execution_review` 应输出 `hold`，并在依据中明确缺失事实和“补齐本周数据”入口；同步完成后回到现有周复盘入口重新计算候选，但不自动推进、创建提案或改写方案。

### 8.6 方案级变化

目标成绩或可训练天数长期变化，或用户有明确起止日期的暂时不可训练区间时，进入方案级调整，而不是修改生命周期状态。用户仍从“时间或安排变了”提交长期星期集合变化，不增加设置页；系统在同一 `plan_id` 的新版本中安排新的可训练边界、休息、降载和恢复衔接，默认从下一个自然周开始生效，当前周继续按现有安排和已确认局部调整执行，不回溯或重排，旧版本保留历史，不创建第二条方案主线。临时日期变化仍按当前自然周 Local Schedule Adjustment 处理。第一版不提供暂停或恢复方案。用户无法给出恢复日期且不再继续备赛时，只能主动结束并归档方案。目标日期变化不属于普通方案版本调整，必须进入目标改期。

**重规划支持赛事延期**：重规划表单选择“赛事延期”时，必须提供结构化“新赛事日期”输入（默认当前目标日期，须晚于今天），而非只写文字原因；重规划候选按新日期重新生成整个周期，用户确认提案后才同步更新目标记录与新方案版本，确认前不修改已生效目标。

**作废方案**：长期方案卡提供“作废方案”入口（确认后执行），标记当前方案 completed 并归档，训练页回到制定方案引导状态；历史版本与执行记录保留，不创建恢复过渡方案。

普通方案级重规划必须展示原阶段/首周负荷与候选阶段/首周负荷、触发原因、执行摘要、生成方式、依据和影响；确认前维持原版本，确认后在同一 `plan_id` 下生成新版本并保留历史。目标改期必须先生成 Goal Rescheduling Preview，展示新日期、替代草稿、与当前方案的差异及风险；生成失败、校验失败、事实变化或预览过期时保留原目标和原方案。只有用户确认仍有效的预览后，才原子废弃旧 `plan_id`、更新同一 Training Goal 并保存预览中的替代草稿。完成比赛、取消或主动结束只归档当前方案并回到无方案状态，不创建模式转换提案。

方案级重规划是一次候选生成，不得为了补充目标可行性、计划执行或恢复结论而串行发起多次在线 AI 请求。系统必须先在本地组装已经过确定性计算的目标、能力、执行、恢复和原方案事实，再一次性交给 `revise-training-scheme`。AI 只返回当前周与下一周的课程骨架，确定性层延展首四周并补全 Workout Steps v2；仍受端到端总预算约束。超时后返回 `scheme_candidate_unavailable`，保留当前方案并只提供用户触发的重试，不保留或展示半成品候选、安全校验结果，也不得改写当前方案。

### 8.7 运动训练内容识别

> 状态：v1 已完成本地实现和自动化测试；已匹配活动的识别名称、置信度可在训练周视图展示。真实多平台历史回放校准和用户纠正界面仍待完成。

系统对跑步活动使用两个相互独立的维度：

| 维度 | MVP 值 | 回答的问题 |
|---|---|---|
| 训练主类型 | 有氧、节奏、间歇、未知 | 这堂课采用了什么主要结构，形成了什么主要刺激？ |
| 地形属性 | 平路、坡地、越野、山地、未知 | 这堂课在什么路线环境和爬升条件下完成？ |

界面可以组合展示为“越野有氧跑”“坡地间歇跑”“山地节奏跑”，但不得让“越野”覆盖“间歇”，也不得仅凭累计爬升把公路坡跑判成越野。

识别依据按以下边界使用：

- 当前活动的时长、距离、配速、心率、功率、步频、分段、爬升和坡度是主要事实；
- 最近训练与身体状态用于建立个人能力基线，并解释相对强度和后续恢复需求；
- 第三方训练类型、活动名称和用户命名只作为辅助证据，不能单独决定结果；
- 历史日报是当时的解释快照，不是训练历史真相源；即使用户此前没有生成日报，系统仍须使用完整原始活动完成识别；
- 当前疲劳可以改变这堂课对运动者造成的刺激和后续建议，但不能反向改变已经发生的分段结构或路线地形。

每次识别必须提供结果、置信度、数据完整度和人能理解的关键证据。证据不足时显示“疑似”或“无法识别”，不得为填满界面强行分类。用户明确纠正后，后续展示和训练建议优先使用用户确认值，同时保留自动结果和版本，便于重新分析与纠错。

识别结果可以：

- 进入日报、周复盘和执行记录；
- 调整平路配速评价，避免把高爬升导致的降速误判为能力下降；
- 统计近期有氧、节奏、间歇和爬升专项分布；
- 作为下一次训练建议和 Adjustment Proposal 的依据，例如避免连续安排高强度或高爬升腿部负荷。

识别结果不得直接修改已生效 Training Scheme、Weekly Plan 或 Daily Workout。需要改变安排时仍须生成结构化 Adjustment Proposal，并由用户确认后生效。

### 8.8 共享单日训练事实与语义摘要

`TrainingDayFact` 是同一用户、同一报告日期的确定性共享事实。它由统一构造器基于已同步的原始活动、健康数据、训练识别和当时生效的方案上下文计算，不依赖历史日报是否存在，也不由自然语言模型决定训练事实。同一输入事实生成稳定的 `summary_version`，调用方不得维护第二套单日解析；同步或事实版本变化时生成新版本，已经归档的日报、周复盘和草稿引用继续指向各自生成时的版本，不静默回写历史。

每个 `TrainingDayFact` 至少包含以下结构化内容：

- **范围与新鲜度**：报告日期（用户本地日期）、`data_as_of`、事实版本和最终性；活动始终按该日期归属，不能因为展示相对日期而移动到前一天或后一天。
- **覆盖状态**：活动、睡眠、恢复、历史窗口分别记录 `complete`、`unsupported`、`missing`、`syncing`、`failed` 或 `insufficient_history`；空活动列表只有在活动覆盖完成时才表示确认休息。
- **实际活动**：每条活动的来源 ID、开始时间、运动类型、距离/时长、关键指标、训练主类型与地形属性（若可识别），以及匹配置信度；原始值和识别值分开保存。
- **计划上下文**：`no_effective_plan`、`draft_available`、`scheduled_plan` 或有效方案版本、当日课次与生效区间。草稿和未来排期只能作为参考，不参与执行评价。
- **结构化证据与缺口**：证据项必须能定位到事实字段或来源记录，缺口项说明缺少的维度及受影响的结论；不能用零值或通用文案填补未知。

证据使用统一结构表达，而非只保存一段不可追溯的文案：每项至少包含 `kind`（事实/覆盖/推断）、`source`（Provider、活动或方案版本）、`field`、`observed_at` 或 `data_as_of`、`value`（可空）和 `confidence`（事实覆盖不适用时可为空）。训练识别的 `evidence`、日报的覆盖快照、周复盘的趋势依据和草稿的能力依据都必须从该结构化证据投影；自然语言只能解释证据，不能成为证据本身。

`review-daily-training` 是单日唯一的 AI 语义复盘 Skill，直接消费已固化 `TrainingDayFact`，同时输出训练内容解释、非枚举运动特点、训练效果、计划执行、恢复反应、能力信号、次日约束、证据、缺口和置信度。原 `summarize-training-day` 的独立调用职责并入该 Skill；旧名称仅保留兼容读取，不再作为草稿、日报或周复盘的额外 AI 请求。AI 语义不可用时，确定性事实、结构化证据和本地结论仍可用，并标记 `semantic_unavailable`，不阻断日报、周复盘或降级草稿。

日报、周复盘和草稿共享事实但拥有不同时间范围和职责：

| 入口 | 事实范围 | 允许产出的结论 | 不负责的写入 |
|---|---|---|---|
| 日报 | 选定本地日期 `D`；活动只归属 `D`，可附带截至 `D` 的有限历史/恢复窗口 | 解释当日发生了什么、数据覆盖、当日计划参考和下一步动作 | 不生成周进程决定，不确认/激活/改写方案 |
| 周复盘 | 用户本地 Natural Week（周一至周日）的全部单日事实，必要时引用此前完整自然周作比较 | 汇总本周实际、变化、风险和下周建议；有生效方案时附加实际执行与待确认进程候选 | 不把周建议直接写入方案；调整只能深链训练页确认 |
| 方案草稿 | 草稿生成时点以前的所需能力/恢复/执行事实；首周基线优先使用上一完整自然周，未来日期仅作为候选排期 | 生成未来训练方案候选、进入阶段和依据 | 不把事实或候选直接激活；确认和版本生效由训练流程完成 |

三类入口复用同一 `summary_version` 和证据字段；它们可以按自身范围聚合或省略维度，但不得各自实现第二套原始活动解析或把自然语言报告当作事实。现有日报/周复盘日期控件、训练草稿的目标与开始日期输入继续作为唯一用户操作入口，不新增“摘要设置”“AI 开关”“证据编辑器”或独立摘要页面；“为什么这样建议”等已有渐进披露区域可展示证据和语义摘要状态。

共享单日事实的验收标准：

1. 同一日期被日报、已完成周复盘和草稿读取时，三者看到的活动集合、覆盖状态、`data_as_of`、缺口和证据定位一致，只允许按各自时间范围聚合或省略。
2. 没有历史日报但原始活动和覆盖证据完整时，仍可创建 `TrainingDayFact` 并供三个入口使用；历史日报不是事实前置条件。
3. 活动覆盖未知、同步中或失败时，事实明确标记状态；不能生成“确认休息”、完成评价或零值负荷结论。
4. `review-daily-training` 超时、拒绝或返回非法结构时，确定性事实、结构化证据和各入口的可用确定性内容仍可读取；不得把单日 AI 失败显示为日报/周复盘/草稿失败。
5. 新事实产生新 `summary_version` 后，用户显式重新生成的日报可以采用新版本；既有报告和草稿仍保留原引用，不能被后台静默改写。

## 9. AI 与用户权限边界

AI 可以读取数据、解释安排、生成调整提案、匹配活动、生成周复盘和发现风险。

AI 不得：

- 未经用户确认修改已生效训练方案；
- 将暂未同步到活动直接判定为用户跳过训练；
- 修改历史计划来美化执行统计；
- 在疼痛场景给出医疗诊断；
- 因一次普通指标波动重写整个周期。

## 10. 产品状态

### 10.1 训练方案

```text
draft → scheduled → active
  ↑         │
  └─取消开始安排
  │         │          ├─目标日期次日→ completed / archived(target_date_reached)
  ├─────────┴─放弃/结束备赛────────→ archived goal + archived scheme
  └─────────┴─确认目标改期预览────→ superseded + replacement draft
```

同一账户在 `draft / scheduled / active` 中合计最多存在一份当前方案；第一版不存在暂停或恢复状态。`superseded / completed / archived` 方案只用于历史解释，不再恢复为当前方案。存量中的旧暂停记录在升级时归档，不进入当前方案读模型。

### 10.2 计划启用与周进程

```text
draft → activation_preview → scheduled → active_bridge → active_standard
                           ↘────────────→ active_bridge / active_standard

entry_review (draft) | execution_review (natural week end)
        ↓                         ↓
   review_pending  ──(user confirms)──> applied
                    └─(keep original)─> unchanged

hold | advance | adjust | deload | replan
```

`active_bridge` 只是“本周剩余安排”的内部兼容状态，不是一个独立训练阶段，也不作为用户需要理解的产品概念。`entry_review` 和 `execution_review` 是同一 `review-training-plan` 工作流的审阅阶段，不新增方案生命周期或页面状态。五种决策先进入 `review_pending`，必须经过用户确认后才应用；用户保持原安排时回到 `unchanged`，不得自动滚动、自动调整或自动重规划。

### 10.3 今日训练

```text
planned
├── adjusted
├── completed
├── partially_completed
├── skipped
└── unmatched
```

`unmatched` 表示没有匹配到运动数据，可以长期保留，不等于用户跳过训练；只有用户明确选择“今天没练”才能进入 `skipped`。迟到的高置信度活动可以通过新的 Execution Record 把当前判断更正为 `completed` 或 `partially_completed`，但不能删除原 skipped 历史。

### 10.4 调整提案

```text
pending
├── approved
├── rejected
├── superseded
└── expired
```

## 11. 异常与降级

- **没有目标赛事**：不生成 Training Scheme；训练页展示已有事实摘要和建立目标入口，活动解释与复盘继续由报告承载。
- **没有平台数据**：必要目标与现实约束完整时生成低置信度、保守起步的唯一草稿并明确说明历史数据不足，不进入额外审批；必要输入缺失时只提示补充。
- **历史能力不可验证**：不要求用户补填原有水平或中断原因；系统降低置信度并生成保守起步方案，现有历史兼容事实只读使用且不直接提高首周负荷。
- **草稿已过时**：草稿后新增训练、约束或恢复风险时先重新生成启用预览；不静默沿用旧首周安排。
- **修改输入后重新生成失败**：保留已确认的 Training Goal 和用户刚填写的页面输入，只显示失败与重试；旧草稿不再展示、确认或作为回退方案，账户仍因 active goal 而不能创建第二个目标。
- **周中或周末启用**：允许当日生效，只生成本周剩余安排，不补齐生效前课次、不计算完整周达成率。
- **确认未来开始**：展示 scheduled 状态和修改日期/取消开始安排入口；生效日前不得作为今日训练或日报执行依据。取消后返回同一方案预览，不释放唯一主线。
- **当前方案期间新建目标或草稿**：从 draft 起隐藏新建入口，API 返回稳定冲突；用户要改变赛事日期时进入目标改期，而不是建立并行目标。
- **放弃目标与方案**：必须明确确认并同时归档 active goal 与当前方案；保留全部历史、释放唯一主线，不物理删除文件。
- **目标改期预览失败或过期**：保持当前目标、当前方案和今日训练不变，允许按最新事实重新生成预览。
- **确认目标改期**：只接受仍有效的预览；原子更新目标、废弃当前方案并保存替代草稿，旧方案保留完整历史，替代草稿确认启用前不提供今日训练。
- **单周跑量异常升高**：结合历史稳定能力和恢复判断；证据不足时输出 `hold`，不提出 `adjust`。
- **同步延迟**：展示“等待同步”，不判定跳过。
- **同步已完成但没有匹配活动**：展示“未匹配到记录”，不得自动判定跳过；用户只能明确选择“今天没练”，不能人工关联或录入活动。
- **用户确认跳过后迟到同步**：同日活动高置信度且无竞争归属时追加执行更正；低置信度保持 skipped，不提示关联候选。两者都不改课表或触发提案。
- **活动数据覆盖未知**：没有运动记录但当天活动同步未完成或状态不可证实时，展示“运动数据未同步/状态未知”，不得判定为休息日；只有活动同步已完成且确无运动记录时，才可标记为已确认休息。
- **AI 服务不可用或请求协议失败**：现有方案仍可查看和记录反馈；新建方案、目标改期替代草稿和完整重新生成展示脱敏失败阶段、原因和统一“重新生成”。缺失数据不触发该失败，只形成带风险说明的降级草稿。
- **完整方案生成失败**：不自动重试；用户明确点击“重新生成”后才从失败阶段发起下一次请求。
- **完整方案生成中**：以异步任务卡显示四段处理状态并禁用重复提交；不显示百分比、模型内部思考或预计时间，也不提供取消按钮。任务可在刷新后恢复轮询，成功后显示唯一草稿预览。
- **疼痛反馈**：立即生成不修改方案的当日安全指引，优先停止当日相关训练或仅保留低强度活动，并在需要时提示进一步评估；保持后续原计划也不能解除该指引，不创建暂停方案或伤病状态。
- **部分完成或跳过**：只保存 Execution Record，不自动补课、顺延或提高后续课程训练量；需要改变安排时生成待确认提案。
- **旅行或时区变化**：按用户当前本地日期展示，保留活动原始时间。
- **重复或多次训练**：匹配前先按 Provider 活动 ID 去重；一个计划课次最多自动关联一条同日活动，其余未占用活动只标记“计划外训练”，不进行多活动拼接。
- **计划外训练**：计入实际负荷和报告，但不抵扣未来课次、不自动调整或生成提案；只有用户点击“重新生成安排”才进入既有提案流程。
- **目标日期已过**：目标日期当天保留比赛安排，次日停止生成训练并自动释放当前方案；已匹配赛事活动时记为 completed，否则以 `target_date_reached` 归档。后续活动同步可以补充赛后结果与报告，但不恢复旧方案或伪造此前完赛状态。
- **并发修改**：旧版本提案不得覆盖新版本方案。

## 12. MVP 范围

### 12.1 必须包含

- 训练主界面和导航入口；
- 从实时活跃方案读取今日训练和本周安排；
- 关键课按顺序展示热身、重复组或连续主体、工作/恢复段、放松、分段强度与完成门槛；AI 候选不得用模糊主体文本替代逐段结构，合同不完整时整次长期生成失败；
- 无方案时复用已有训练目标的分步建立向导与草稿确认流程；
- 当前可持续能力、历史已证明能力、中断背景与数据置信度的分层展示和用户纠正；
- 启用预览、开始日期选择、本周剩余安排和首个完整训练周；
- 草稿生成时的 `entry_review`、每个完整自然周后的 `execution_review`，以及五种决策（`hold`、`advance`、`adjust`、`deload`、`replan`）的证据、风险和确认入口；
- “时间或安排变了”“身体状态不好”“疼痛或不适”三个课前反馈入口；
- 调整前后差异、影响和原因；
- 用户确认后生效，并分别保留局部调整记录或长期方案版本；
- 运动数据自动匹配和训练后反馈；
- 基于完整原始活动的训练内容分析，支持训练主类型与地形属性分轴识别；
- 识别结果、置信度、关键证据和低数据质量降级展示；
- 移动端适配、结构化 API 和配套 MCP 能力。

### 12.2 暂不包含

- 拖拽式日历编辑；
- 多目标并行训练；
- 社交分享或真人教练协作；
- 自动写入外部平台训练日历；
- 复杂比赛预测模型；
- 依靠视频或地图路面识别推断越野表面；
- 无用户确认的训练方案自动改写；
- 用 neurun 派生负荷覆盖第三方原始训练负荷；
- 完整伤病诊断或康复计划；
- Web 通用聊天、聊天历史或流式对话接口；当前 AI 只服务于日报、周复盘、方案草稿、局部调整解释、方案重规划和比赛策略六条显式旅程。

## 13. 交付阶段

1. **可感知（已实现）**：训练主界面、实时方案、今日训练、本周安排、旧方案迁移和无方案状态。
2. **可交互（已实现）**：训练反馈、规则校验后的调整提案、差异确认、版本管理和 MCP 能力。
3. **可执行（Workout Steps v2 核心已实现）**：新方案已生成并校验重复组、快慢段、分段强度、个人目标/体感降级、结构化完成标准和时间轴；旧 v1 方案保持只读兼容。日报已携带计划逐段结构，但真实 Provider 分段与每组完成证据的自动匹配仍待实现。
4. **可自适应（部分实现）**：Athlete Capacity Profile、Activation Preview、排期启用、排期取消、目标改期预览/确认、本周剩余安排、`review-training-plan` 的基础审阅、训练前说明、周复盘和方案级修订提案已实现；严格跨文件原子恢复、完整阶段状态机、赛后复盘和由审阅决策自动形成方案级提案仍待实现。训练活动只做同日单活动自动匹配，不建设拆分、替代或人工纠正。无赛事滚动排课和教练模式转换已移除（2026-08-12）；教练模式由生效方案派生，不再有待确认提案。

正式发布至少包含“可感知”和“可交互”，否则没有解决无法交互式迭代的问题。

当前实现不会把规则引擎包装成 AI 自动决策：在线教练不可用时，反馈仍可生成经过确定性安全约束的保守提案；提案的来源和数据依据会保留，用户确认边界不变。运行界面目前仍保留时间不足、疲劳、疼痛和日程冲突四类旧快捷入口，后续实现按本文件收敛为三个入口，并同步 Web API 与 MCP schema。

## 14. 验收标准

- 在任一主题下从训练切换到“报告 / 同步 / 我的”，页面背景、卡片、文字、强调、警示和危险色保持同一主题令牌；训练页面不得因模块不同而呈现另一套暗色或运动色方案。
- 训练完成、等待匹配、警示等状态继续提供文字标签，不能只依靠颜色区分。

- 活跃方案变更后，无需重新生成日报即可在训练页看到最新内容。
- 没有方案时存在明确的创建入口，不展示空白指标。
- 没有当前方案且存在唯一 active Training Goal 时，建立向导自动选中且不要求重复填写；形成草稿后不能创建第二个目标或第二份草稿。存量多个 active goal 必须先由用户保留一个、原子归档其余目标，不能由系统猜测。
- 没有训练目标时可在向导内快速创建；之后仍只在训练页管理或选择该目标。
- 向导按目标赛事、现实约束、方案预览与开始确认三个页面推进，并允许返回修改；能力档案不成为第四个必经页面。
- 最近活动覆盖不足时，现实约束页仍只询问常规星期集合与统一单次最长时间；预览显示数据不足，不追加动态能力问题，也不把缺失活动解释为零训练量或休息。
- 建立方案不提供早晚时段、逐日最长时长、日期例外、请假或旅行日历；方案生效后的临时不可训练安排从“时间或安排变了”提交，不能回到建立向导扩展约束模型。
- 赛事、距离、日期、可训练日和单次最长时间完整但历史运动数据不足时，仍生成低置信度、保守起步的唯一方案并正常一次确认；不得进入独立 `insufficient_data` 审批状态。
- 缺少任一必要输入时才阻止方案生成并提供对应补充入口；可选目标成绩和历史能力信息缺失都不能单独阻断生成。
- 核心准入通过后，草稿生成前只展示一次可跳过的 `additional_context` 短文本窗口；字段最多 280 个 Unicode 字符，用户必须选择“提交并生成”或“跳过并生成”，空提交按 `no_additional_context` 处理并继续生成。
- 补充信息不作为 Training Goal、现实约束、能力档案或 Training Scheme 的长期字段；提交前不自动保存，任务终态后清除原文，最多保留 24 小时脱敏审计元数据，报告、训练记忆和方案历史不回显原文。
- 有效补充信息只作为同一次 `draft-training-scheme` + `review-training-plan(entry_review)` 请求中的未验证 `user_supplement` 上下文；它不能覆盖确定性事实、硬性目标或安全底线，冲突必须展示为不确定性或审阅依据。
- 补充信息超长、非法、过滤失败、存储异常或 AI 处理失败时，核心准入通过的请求自动降级为无补充信息路径并继续草稿生成，标记 `supplement_unavailable`；不得因补充信息失败显示无草稿或触发第二次模型调用。
- 补充信息窗口不新增页面、设置、历史列表、聊天线程、复杂问卷或第二次确认；用户只能在现有建立向导/草稿预览中输入、清空、跳过并查看简短采用状态。
- 方案预览的“为什么这样安排”只读展示当前状态、当前可持续能力和历史已证明能力；不提供当前周跑量、历史稳定水平或中断原因的填写与纠正入口。
- 历史 PB、峰值周跑量或单次大训练不会直接成为当前首周目标；系统同时展示最后证明时间、中断背景和置信度。
- 用户近期因为出差或短期主动休息低于历史稳定水平时，系统可计算更快但仍受安全范围约束的恢复安排；伤病、疾病或长期停训只能生成保守安排，页面不提供策略选择器。
- 草稿的周量/负荷基线固定取上一完整自然周（周一至周日）的实际运动；当前未结束周、最近 7 天滚动量和动态周数据不得直接进入草稿基线。上一周只作为事实参考，不能原样复制跑量或课表；草稿必须先由 `entry_review` 判断当前能力、训练连续性、有氧基础、近期表现、恢复与目标是否支持缩短适应周期/提前进入更高阶段，再决定是否小幅拔高。上一周数据缺失或覆盖不足时，标记数据不足并使用保守固定基线，不把当前周缺失解释为零训练。
- 草稿 AI 输入只包含方案决策最小事实集：目标与现实约束、当前能力、上一完整自然周实际周量、当前阶段已确定的建议周量目标、最近两个已结束自然日训练摘要、事实版本/截止时间、恢复/覆盖/缺口和全部适用安全边界；不得因载荷压缩删除其中任一项。
- 最近两个已结束自然日出现长距离或质量课时，压缩后的输入仍能触发次日不排强度的既有衔接规则；任一日覆盖未知时必须按未知事实传递，不能压缩为空列表或休息日。
- 任务 ID、阶段状态、等待/请求耗时、重试次数、Provider HTTP 状态、调用 trace、调试序列化字段、原始模型响应和内部 handoff 文本不得进入草稿 AI 决策载荷；仅这些运行元数据变化时，业务事实投影必须保持一致。
- 草稿载荷压缩前后使用相同的 Schema、处方补全和安全校验；恢复状态、周量基线/目标或安全边界投影失败时必须显式降级或阻断，不得以零值、空值或默认正常状态继续生成。
- 周跑量作为系统建议的方案负荷展示，用户不需要在选择目标时自行给出；建议必须说明数据依据。
- 方案预览中的周跑量、具体训练日期、课程类型、训练步骤和单课内容全部只读；页面必须展示当前周和下一周的具体日期，但不提供拖拽、替换、增删或数值编辑，API/MCP 也不能提交这些输出字段。`weekday` 仅为 AI 与确定性排期层之间的相对星期合同。
- 完整周期的阶段顺序必须保持基础/适应→专项强度→高峰→减量；`entry_review.advance` 只决定建议切入点，不自动跳过阶段、倒置阶段或改变用户尚未确认的后续安排。发现倒置时记录非阻断审阅项，交由重新生成或确认处理。
- 方案预览仍返回并校验完整首四周；其中当前周与下一周来自 AI，后两周由确定性延展。页面默认展开候选首周，第二至第四周只展示周跑量、关键课和训练目的摘要，并允许就地展开完整逐日课程。展开不发起生成请求、不持久化新状态，也不改变确认对象。
- 草稿预览默认按“方案逻辑 → 当前切入阶段 → 当前周/下一周执行明细 → 后续周期摘要”展示；方案逻辑必须说明能力、负荷和周期取舍，切入阶段必须说明依据和适应周，当前周与下一周必须显示跑动安排、距离或时长、配速/体感和训练目的；数据依据、样本、事实截止时间、规范化调整和不确定性统一放入可发现的“为什么这样安排”折叠区。
- 预览首屏不得展示 Skill 名称、调用 trace、ACWR 原始数值、候选 JSON、完整 Workout Steps v2 或内部 handoff 字段；安全提示、当前切入结论和用户确认入口不得折叠。
- 训练详情只展示当前方案版本和最近一次调整；历史版本、版本差异、撤销和恢复不进入用户页面，也不由 Web/API/MCP 提供浏览或操作入口。后台继续保留不可变版本和审计记录。
- 用户修改目标、可训练日、单次最长时间或开始日期后，系统重新生成并校验同一份唯一草稿；不得把输入修改实现为对旧课程的局部覆盖。
- 新输入提交后旧草稿立即不可读取和确认；重新生成成功后只能读取最新内容，旧草稿不进入方案历史、调整记录或任何用户可见列表，也不能比较、撤销或恢复；失败时页面只提供重试，不回退展示旧草稿。
- Training Scheme 引用 Training Goal；修改目标不会静默改写已生效方案。
- 今日训练同时包含可执行内容和安排原因。
- 每份非休息今日训练展示训练块、距离/时长优先级、完成要求、调整边界和通俗强度表达；RPE 不得作为唯一强度说明。
- 间歇、变速、法特莱克、重复跑和含专项配速段的长距离必须展示可按顺序执行的步骤；重复主体明确组数、工作段、恢复段、各段计量方式和进入下一组的条件，不得只写“交替完成”或“按课程要求完成”。
- 每个工作段与恢复段分别携带相对强度目标；数字配速、心率或功率只在该段存在匹配的个人事实时展示，否则使用明确的体感、呼吸、动作质量和结束余量作为降级目标。
- 页面以时间轴或等价顺序结构展示热身、重复组、放松和完成进度；折叠摘要仍至少显示组数与快慢段结构，不能退化为课名、总距离和单个 Zone。
- 可行目标只展示唯一 AI 方案候选；不可行目标只展示一条不含周期和课程的 Feasibility Recommendation，不展示路线列表或预生成并行草稿。
- `challenging` 方案在同一预览内展示风险和取舍，主动作仍为一次“确认该安排”；不得增加二次弹窗、额外勾选或独立风险确认状态。
- Feasibility Recommendation 只允许用户“接受建议”或“修改目标”；接受时必须校验目标版本，成功更新同一目标后才重新生成唯一草稿，过期建议不得覆盖新目标，且接受建议本身不启用方案。
- AI 超时、结构化输出不完整，或不可行结论没有给出一项合法目标修改时，不保存规则补全方案或不完整建议，只显示失败与重试。
- 逐段处方的各步骤合计必须与课程总量一致，完成标准能够判断完整完成、减组完成或未完成；日报不得只比较总距离。
- 若轻松/恢复课的总距离与总时长隐含配速明显快于近期个人参照，页面必须显示“安排待修正”，将本次执行收紧为单一安全目标，并保留原安排供用户重规划；不得展示成可执行的双目标课程。
- 个人配速或心率事实不足时，页面明确使用可对话等体感表达，不得展示伪精确区间。
- 有可靠个人事实时，训练详情默认按训练块展示基础配速区间和当天执行区间；依据、样本数、事实截止时间和置信度通过“为什么这样建议”入口展开，Z5 区间必须绑定工作段时长或距离。
- 所有训练推荐默认只展示结果、下一步和必要安全状态；推荐理由不得在首屏连续铺开，但必须存在可发现、可键盘操作的展开入口。展开/收起不触发生成、写入或推荐变化。
- 当天先以当前能力和近期表现确定执行基线；目标导向推进仅在状态稳定且存在生效目标时允许小幅发生，并且只改变当天只读区间。恢复异常可以抵消推进或取消数字目标；ACWR 高但恢复和表现稳定时只显示风险提示，不单独改变配速。任何基础配速上调仍须新增证据并经重新校准或确认提案，不能静默改写方案。
- 新增可靠同类训练后可重算配速校准档案；若重算结果需要提高基础配速或改变课程结构，必须生成待确认调整提案，确认前今日训练、本周安排和长期方案保持不变。
- 坡地、越野、极端天气、疼痛、恢复异常、样本不足或证据冲突时，系统不得把普通平路整体均速伪装成精确配速处方，并必须解释降级原因。
- 训练页首要信息只包含今日怎么跑、本周怎么跑/进度如何和后面几周安排如何；待确认决策不被任何折叠层级隐藏。
- 训练页所有按钮统一 13px 字号且文字不换行；窄屏（≤600px）下卡片头部（标题 + 操作按钮/收起按钮）自动换行，日期区间与“查看本周进度”等操作不得互相挤压。
- 间歇、节奏、变速和长距离等课程由阶段、能力、恢复和安全边界编排，不能由固定课程枚举或随机模板单独决定。
- 日报按同一训练处方比较训练块、总量和强度，区分完全完成、部分完成、跳过、等待同步与不适用；周推进不在日报中自动决定。
- 部分完成和跳过不会创建补课队列，不会把未完成训练量转移到次日或本周其他课程，也不会改变既有周安排；只有新的待确认提案可改变后续课表。
- 没有匹配活动时始终保持 `unmatched`，同步完成、日期结束或周复盘都不能自动转为 `skipped`；只有用户明确选择“今天没练”才能记录跳过。
- 周复盘单独展示 unmatched 数量，不把它计作漏练或已完成，也不基于 unmatched 单独生成调整提案；存在会实质影响判断的未匹配关键课时降低数据置信度或返回“数据不足”。
- 用户确认跳过后出现高置信度迟到活动时，系统以新 Execution Record 自动更正为完成或部分完成并保留 skipped 历史；低置信度候选不能改变当前状态。
- 计划休息日训练或计划课之外的第二次活动只标记“计划外训练”并计入实际负荷；不得自动抵扣未来课次、换课、生成提案或重排，用户只能显式点击“重新生成安排”发起候选。
- 本周进度和周复盘不展示综合完成率或加权分数，只展示计划量/实际量及 completed、partially_completed、skipped、unmatched、unplanned 的独立计数；进程判断不得读取合成分数。
- “调整今天”只展示三个课前入口；天气、场地和日程冲突可作为“时间或安排变了”的原因提交，但不显示成额外快捷功能。
- 训练后感受只从完成记录提交，不与课前调整入口混排；三个课前入口都能产生包含原值、新值、原因和影响的提案。
- 疼痛反馈提交后，今日训练立即显示当日安全指引并隐藏原强度的可执行状态；该指引不产生方案版本，拒绝后续提案也不能解除。
- 未确认提案不会改变今日训练、本周安排或长期方案。
- 只影响今天或当前自然周的提案确认后只形成局部安排记录，不增加 Scheme Version、不废弃当前方案；改变后续周负荷、阶段结构、关键课演进或目标路线时才在同一 `plan_id` 下生成新 Scheme Version。
- 局部安排保留原课次与调整后课次并参与执行比较，不能跨周或改变长期方案边界；并发批准以当前周安排修订号校验，旧提案不能覆盖较新的局部安排。
- 调整提案只提供“确认调整”和“保持原计划”；补充事实会创建新的结构化反馈，不会建立对话线程或原地改写提案。
- 同一方案版本和调整范围已有待确认提案时，新反馈只有在新提案成功落盘后才将旧提案原子标记为 `superseded`；生成失败时旧提案仍可决策，任一时刻只暴露一份待确认提案。
- 重复确认同一提案不会重复创建版本。
- 旧版本提案不能覆盖更新后的方案。
- 同步延迟和无法匹配不会被错误标记为跳过。
- 空活动列表不会单独触发“休息日”；同步覆盖未知时，日报、教练上下文和历史明细均显示运动数据状态未知。
- 方案在某日之后才确认启用时，该日前的日报和历史教练查询均显示“当日尚无生效计划”，不得反向生成课次或评价未执行。
- 报告日已有草稿时显示“当日已有待确认方案草稿，仅供参考”；已有未来启用安排时显示正式开始日。两者执行状态均为“不适用”，但不得显示成“完全没有方案”。
- 启用前页面只展示一个推荐开始安排和“修改开始日期”入口；确认时间、正式生效日和首个完整训练周分别保存。
- 用户确认未来开始日期后看到 scheduled 状态；生效日前不出现该方案课次。修改日期会使旧启用预览失效并生成新的启用安排；取消开始安排会回到同一方案预览，目标和方案内容不丢失、唯一主线不释放。
- 草稿/预览中的“放弃目标与方案”和 active 状态的“结束备赛”都必须同时归档 active goal 与 current scheme、保留历史并释放主线；任一步失败时两者都维持原状态。
- draft、scheduled 与 active 当前方案互斥；任何日期和任何实时读模型都不能同时返回两份当前方案，不存在暂停/恢复分支。
- 有明确起止日期的暂时不可训练区间通过待确认调整提案写入同一 active 方案；没有恢复日期且不再备赛时，用户结束方案并归档。
- 用户提交新目标日期时，当前目标和方案持续有效，改期预览不是第二份当前方案，也不生成可执行课次。
- 改期预览生成失败、事实发生变化或预览过期时，原目标与方案保持不变；用户确认有效预览后，旧方案与新草稿切换不得出现半完成状态。
- 用户确认目标改期后，旧方案进入 superseded 历史，预览中的替代安排成为唯一待确认草稿；旧方案不再生成未来课次，新草稿不反向改变历史日报。
- 目标日期当天仍能读取比赛安排；次日任一训练读写都会幂等结束 current scheme，匹配赛事活动时为 completed，否则以 `target_date_reached` archived，并立即允许建立下一目标。
- 周中或周末启用时只生成覆盖剩余日期的本周剩余安排，不补齐生效日前训练、不强求完整周目标、不计算完整周达成率且不计作阶段周。
- 草稿生成后出现新训练或能力事实变化时，启用预览展示事实差异并要求刷新，不静默使用旧负荷。
- 同一 `plan_id` 的新版本生效后，历史日期仍解析到覆盖该日期的旧版本；日报固化方案版本、生效区间和当日课次证据。
- “当日尚无生效计划”与“生效方案安排休息日”具有不同机器状态，只有后者可以参与计划执行统计。
- 计划量与实际量按用户本地自然周（周一至周日）比较，上一自然周末的活动不会进入本周实际量；周视图并列展示 `target_km`、`target_load`、课程结算值和实际值，不额外计算综合完成率。
- `target_km` 或 `target_load` 与课程累计不一致时，确定性 reconciler 先按安全边界调整或以课程累计值结算，并把原值、新值、差异、原因和结算方式写入 `adjustments`；仅因该差异不得阻断草稿或周计划生成。
- 草稿生成采用 `TrainingFramework` 与 `NearTermSchedule + entry_review` 两个在线 AI 阶段；每个完整自然周结算后必须单独执行一次 `review-training-plan(execution_review)`。两种审阅都只能输出 `hold`、`advance`、`adjust`、`deload`、`replan` 之一，并展示能力、执行、恢复、目标/课程结算和数据完整性证据。
- `entry_review` 可安全应用的修正直接写入待确认草稿；未应用建议只进入 handoff，用户主动重新生成时才作为新约束使用。`execution_review` 只作为下一步候选，必须在现有周复盘/调整入口由用户确认后，才生成局部安排或新 Scheme Version。
- 用户未确认或选择保持原安排时，当前方案、Weekly Plan、目标和今日训练保持不变；`advance` 也不得在自然周结束后自动滚动，`adjust`、`deload`、`replan` 需展示原安排与建议差异后再应用。
- 审阅结果复用现有草稿预览、周复盘和调整确认入口，不新增复杂页面、设置项、课程编辑器、聊天线程或第二次确认页面；展开解释不触发生成或写入。
- AI 不可用时，已生效方案仍可完整查看。
- 新建、改期替代草稿或生效方案完整重规划的数据缺口默认不阻断，生成结果标记“部分信息缺失”并展示缺口、风险和补充入口；只有 AI 无可用框架/课表、Schema/Normalizer/Validator 无法形成可执行结果或明确安全底线不允许执行时才不写草稿，原目标与生效方案保持不变。
- 失败后的唯一主操作文案为“重新生成”；只能由用户点击触发，并按失败阶段断点续跑，页面刷新、重新进入、`Retry-After` 到期或网络恢复都不得自动发起请求。
- 完整方案请求期间显示与同步一致的四段阶段列表；不显示百分比、模型思考、预计时间和取消按钮，刷新页面后按任务 ID 恢复轮询。服务端收到完整可解析的上游 JSON 后立即处理。
- AI 服务 JSON 输出协议发生回归时，贡献 Skill 请求不会仅因缺少供应商要求的提示词而返回 400；若上游仍拒绝请求，降级原因至少包含脱敏错误类型或提示，且不泄露密钥、完整 Prompt 或训练事实。
- AI 阶段周数与赛事时间线不一致但阶段结构完整时，系统规范化到真实总周数、展示调整差异并保留 AI 风险与路线建议，不得整份降级为规则方案。
- 疼痛反馈不会产生继续加量或提高强度的默认建议。
- 没有历史日报但存在完整活动数据时，训练内容分析仍能正常运行。
- 有氧、节奏和间歇按个人能力基线判断，不使用单一固定配速作为全部用户的分类标准。
- 具有重复工作—恢复分段的训练可识别为间歇；稳定连续且接近个人阈值的主体段可识别为节奏。
- 同一活动可以同时具有训练主类型和地形属性，例如“坡地间歇跑”。
- 只有爬升证据时不得自动判定为越野；缺少分段或个人基线时结果明确降级并展示原因。
- 山地或坡地训练进入后续恢复和排课建议依据，但不会未经确认修改已生效方案。
- 用户纠正结果后，后续分析使用确认值，自动推断与算法版本仍可追溯。
- 320px 宽度下关键信息和操作不重叠、不横向滚动。

## 15. 产品观察指标

先采集基线，不预设缺乏数据依据的目标值：

- 方案草稿确认率；
- 活跃方案用户的训练页访问频率；
- 今日训练查看率；
- 反馈到提案、提案到确认的转化；
- 提案确认、保持原计划和被新反馈替代的分布；
- 计划训练与实际活动的匹配率；
- 调整后与未调整课次的完成情况差异；
- 用户确认后短期撤销或再次调整的比例；
- 启用预览中推荐日期的直接确认率、用户修改日期的比例，以及系统内部起始路径分布；
- 草稿因新训练或能力事实变化而刷新预览的比例；
- `hold / advance / adjust / deload / replan` 分布及用户确认率；
- `adjust` 或 `replan` 确认后两周内再次降载、疼痛反馈或撤销调整的比例；
- 疼痛场景未经确认自动改变方案的次数，要求为零。

## 16. 已确认决策

- 用户可见名称使用“训练方案”，不使用“运动大纲”。
- 训练主界面采用“今日怎么跑 → 本周怎么跑/进度如何 → 后面几周安排如何”的信息优先级。
- 结构化页面是当前唯一产品界面；解释和调整通过六条显式工作流及确认式操作完成，不建设通用 Chat。
- AI 只能创建调整提案，用户确认后新版本才生效。
- 调整提案不承载继续讨论；用户只确认调整或保持原计划，补充事实通过新的结构化反馈生成替代提案。
- 课前反馈入口固定为“时间或安排变了”“身体状态不好”“疼痛或不适”；天气与场地归入安排变化，训练后反馈归入完成记录。
- 疼痛反馈先产生无需确认的当日只读安全指引；长期调整仍需用户确认，“保持原计划”只作用于后续方案，不能恢复当天原强度。
- 当日和当周现实变化确认后形成 Local Schedule Adjustment，不升级长期方案版本；只有跨周负荷、阶段结构、关键课演进或目标路线变化才形成新 Scheme Version。
- 漏练或部分完成只进入 Execution Record，不自动补课、顺延或压缩后续训练；系统只能在影响实质化时提出待确认调整。
- `skipped` 只来自用户明确的“今天没练”；未匹配活动无论经过多久都保持 `unmatched`，周复盘单独展示且不据此推断漏练。
- 用户确认跳过后出现同日、高置信度且无竞争归属的迟到活动时，系统追加执行更正而不要求再次确认；低置信度保持原状态且不提供人工关联，任何更正都不改变方案或周安排。
- 第一版训练活动只做同日、单活动的高置信度自动匹配；课程未匹配时用户只能选择“今天没练”，不建设活动选择器、手动录入、跨日替代或多活动拼接。
- 第一版不把不同训练自动判为“替代完成”；不符合高置信度计划课证据的活动只标记为计划外训练或保持未匹配。
- 训练后不提供完成或部分完成手动按钮；活动匹配自动产生执行状态，用户只能补充体感、疼痛和完成质量，或明确选择“今天没练”。
- 计划外训练只打标并计入实际事实；系统不自动处理，用户需要时从“重新生成安排”主动发起待确认候选。
- 周执行不生成综合完成率或加权评分，只展示 `target_km`、`target_load`、课程结算值、实际量和五类执行状态计数；统一 `review-training-plan` 直接读取 reconciler 与执行事实。
- `target_km` 与 `target_load` 是目标而非生成硬约束；课程累计不一致时由确定性 reconciler 调整或按课程累计值结算，并在 `adjustments` 中保留差异与原因，不能仅因不一致阻断生成。
- `review-training-plan` 统一包含草稿生成同次请求中的 `entry_review` 和自然周执行结束后的 `execution_review`，固定输出 `hold`、`advance`、`adjust`、`deload`、`replan`；entry 阶段仅允许把安全、局部修正写入待确认草稿，任何方案激活或执行阶段决策都必须用户确认后才生效，系统不自动推进或改写生效方案。
- 审阅结果复用现有草稿预览、周复盘和调整确认入口，不新增复杂页面或课程编辑器；用户展开解释不触发重新审阅、写入或自动推进。
- 完整训练方案只有 AI 候选骨架通过 Schema、确定性处方补全和最小执行底线校验才能形成；Validator 只阻断无法解析、字段非法、步骤不可执行等系统底线。周期、负荷、恢复、配速和训练安排质量由同次 AI 审阅输出非阻断建议，存在 `safety_hold` 时由用户确认后再采用，不生成第二套长期方案。
- 目标不可行时只给一条 Feasibility Recommendation：优先放宽可选成绩目标，只有赛事日期无法支持安全周期时才建议改期；用户接受或自行修改目标后再生成唯一方案。
- `challenging` 仍是可确认的唯一方案预览，风险直接展示在预览中，不建立二次确认流程；只有 `not_recommended` 阻止生成方案并要求先修改目标。
- 建立方案时，必要输入缺失就直接补充，只有历史证据不足则生成低置信度保守方案；`entry_review` 和 `execution_review` 的五种决策不得另建 `insufficient_data` 方案状态，数据不足时以 `hold` 输出并说明缺口。
- 方案课程内容始终由 AI 候选和 Validator 整体产生，预览阶段不允许用户直接编辑课程；用户只能修改输入并重新生成，不建设课程编辑器。
- 启用前只存在最新草稿，不保留草稿版本历史；只有确认启用后的 Scheme Version、执行事实和调整记录长期保留。
- 目标、能力事实或现实约束改变后，旧草稿立即失效；新草稿生成失败时进入“无可确认草稿”页面，而不是恢复旧草稿或新增 stale 生命周期状态。
- 建立方案不提供独立能力编辑：周跑量、历史稳定水平和中断原因由系统从事实推断并只读解释，用户只修改目标、可训练日、单次最长时间和开始日期。
- 建立方案的 Weekly Training Availability 只包含常规星期集合和统一单次最长时间；不建设时段、逐日时长或日期例外配置，临时安排变化复用训练反馈。
- 临时改日期不增加设置页；反馈确认后只形成当前自然周局部安排，保留目标、当前方案和历史版本，不把一次日期变化当作改期或放弃方案。
- 长期可训练日变化也复用“时间或安排变了”入口，提交新的常规星期集合后在同一 `plan_id` 下生成待确认 Scheme Version；旧版本保留，不创建第二条方案主线。
- 长期可训练日变化默认从下一个自然周开始生效；当前周不回溯、不重排，继续使用当前 Weekly Plan 和已确认的 Local Schedule Adjustment。
- 长期可训练日变化生成失败时保持当前方案和本周安排不变，不写入半份 Scheme Version；页面只提供明确失败提示和用户主动点击的“重试”，不自动重试或后台补写。
- 方案读模型继续包含完整首四周，但 AI 只负责当前周和下一周；后两周由本地规则从阶段、负荷边界和第二周课程骨架延展。预览只在展示层渐进披露：候选首周默认展开，第二至第四周先显示摘要并可按需展开，不新增编辑、生成或保存流程。
- 用户界面不展示方案版本时间线、历史版本列表、差异对比、撤销或恢复；不可变历史版本、调整提案和审计记录仍由后台保留，用于按日期解释历史训练和故障追溯。
- 完整方案生成失败不自动重试；用户点击“重新生成”只重跑失败阶段，已成功且版本一致的中间结果继续复用。
- 完整方案生成态显示四段本地阶段提示并禁用重复提交，不显示百分比、模型思考或预计时间、不提供取消按钮；刷新后恢复任务轮询。若上游已经交付完整可解析结果，页面应继续得到预览或明确的本地校验失败。
- 第一版训练板块只服务明确目标赛事；没有目标赛事时不生成滚动方案，只提供建立目标入口和跨页查看报告。
- 训练内容采用“训练主类型 + 地形属性”双轴模型，不做有氧、节奏、间歇、越野四选一。
- 训练识别直接读取完整原始活动和个人基线，历史日报只保留生成时快照。
- 识别结论可以影响训练建议和调整提案，不得直接改写生效方案或覆盖平台原始负荷。
- `Athlete Baseline` 只负责近期相对强度解释；跨时间训练能力统一使用 `Athlete Capacity Profile`。
- 草稿确认时间、正式生效日期和首个完整训练周独立；用户可在周中立即生效，本周剩余安排不计阶段周，下周一进入首个完整周。
- 未来开始的已确认方案处于 scheduled，不提前成为当日执行依据；改期或取消通过 Activation Schedule 处理，不篡改历史日报。
- 一个账户只有一条当前训练方案主线；从草稿形成起就不能创建新目标或并行草稿。目标改期先生成不生效预览，确认有效预览后才原子废弃旧方案并提交替代草稿。
- 目标日期为当前方案的硬结束边界；次日自动结束并释放主线，不建设赛后恢复方案，赛后事实继续由报告承载。
- 当前可持续能力决定训练从哪里开始，历史已证明能力决定可恢复上限和推进观察窗口，历史峰值不能直接成为当前负荷。
- 训练进程由完整周的执行质量和身体适应驱动，而不是按日历机械升级；重大 `adjust` 或 `replan` 仍需用户确认。
- 日报、周复盘和方案草稿统一读取确定性的 `TrainingDayFact` 与结构化 evidence；`summarize-training-day` 只提供可选语义解释，AI 不可用时不阻断事实读取、周复盘或草稿流程，也不新增摘要设置或页面。
- 草稿生成前增加一次可跳过的轻量补充信息窗口，仅收集最多 280 字的 `additional_context`；它是本次请求的临时用户上下文，不是能力、目标、现实约束或长期偏好字段。
- 补充信息只有在用户明确提交后才按 `request_id` 冻结并进入同一次草稿 prompt；空值/跳过、校验失败、存储异常或 AI 处理失败均按无补充信息路径继续，不增加模型调用、页面或确认步骤。
- 原始补充文本只在任务生命周期内短期保存，终态立即清理；长期只保留脱敏状态与采用结果，不把原文写入报告、记忆、Training Goal、Training Scheme 或方案历史。
