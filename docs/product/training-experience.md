# 产品方案 — 训练体验与交互式训练方案

> 版本: v0.1 · 日期: 2026-07-28
> 状态: 产品方向已确认，尚未实现
> 配套技术设计: [training-system.md](../design/training-system.md)

## 1. 背景与问题

当前运动大纲主要以 AI 记忆和日报摘要存在。用户只能感知训练阶段、剩余周数、周跑量目标等少量信息，无法持续看到今天做什么、本周如何推进、计划为何变化，也没有“反馈现实约束—查看调整差异—确认生效”的协作闭环。

训练能力需要从隐藏的文档型记忆升级为用户每天可进入、可理解、可反馈、可确认调整的核心产品体验。

## 2. 产品目标

训练主界面持续回答四个问题：

1. 我今天练什么？
2. 为什么这样安排？
3. 我这周和长期目标进展如何？
4. 如果现实情况变化，计划如何安全调整？

目标闭环：

```text
训练目标 → 训练方案 → 周计划 → 今日训练
                         ↓
                 运动数据 + 主观反馈
                         ↓
              AI 调整提案 → 用户确认
                         ↓
                 新方案版本生效
```

## 3. 目标用户与训练模式

MVP 优先服务有明确跑步目标的用户，例如目标赛事、目标距离或目标成绩。训练方案以目标日期和训练阶段为主轴。

没有比赛目标的用户进入兼容模式：系统根据训练频率、健康状态和一般目标生成滚动四周方案，不强制展示“距比赛还有几周”。

## 4. 产品原则

- **行动优先**：先展示今天做什么，再展示长期理论。
- **可解释**：训练安排说明训练目的、数据依据和对后续计划的影响。
- **用户确认**：AI 可以生成调整提案，但不能静默覆盖已生效方案。
- **实际闭环**：运动平台数据负责证明实际完成情况，用户补充主观感受和现实约束。
- **安全优先**：疼痛、疾病和异常恢复进入安全流程，不以完成率为第一目标。
- **渐进披露**：首页保持简单，训练阶段、配速体系和完整版本历史按需展开。

## 5. 统一产品语言

| 概念 | 回答的问题 | 变化频率 |
|---|---|---|
| 训练目标 | 用户要达到什么结果？ | 很低 |
| 训练方案 | 总体如何达到目标？当前处于什么阶段？ | 每几周或发生重大约束变化时 |
| 周计划 | 这周具体练什么？ | 每周，可随状态调整 |
| 今日训练 | 今天具体做什么？ | 每天 |
| 执行记录 | 实际做了什么？ | 每次训练后 |
| 训练反馈 | 用户感觉如何、遇到了什么约束？ | 随时 |
| 调整提案 | 建议修改什么，为什么？ | 按需 |
| 方案版本 | 用户确认后生效的方案快照 | 每次确认调整后 |

用户界面统一使用“训练方案”，不再将“运动大纲”“训练计划”和“今日建议”混为同一个概念。

## 6. 信息架构

### 6.1 主导航

MVP 使用四项主导航：

```text
训练 | 日报 | 同步 | 我的
```

训练成为核心业务入口，但 MVP 不强制替换现有日报默认首页。同步完全自动化后，可将同步降级为状态入口，主导航收敛为“训练 / 日报 / 我的”。

### 6.2 训练模块

```text
训练
├── 今日训练
├── 本周安排
├── 训练方案
│   ├── 目标与约束
│   ├── 阶段路线
│   ├── 周结构
│   ├── 强度与恢复边界
│   └── 版本记录
└── 调整记录
```

## 7. 训练主界面

### 7.1 首屏

用户无需滚动即可看到：

- 当前目标、目标日期和训练阶段；
- 今日训练名称、距离或时长、配速或心率区间；
- 今天这样安排的原因；
- 当前恢复状态是否影响原计划；
- 查看详情和“调整今天”入口。

首页信息优先级固定为“今日训练 → 本周安排 → 长期方案”，不得只显示阶段、剩余周数和周公里数等抽象状态。

### 7.2 本周安排

本周视图同时展示七天计划，并区分：

- 已完成、部分完成、替代完成、跳过、待训练和等待匹配；
- 关键训练、恢复训练和休息日；
- 原计划与调整后的安排；
- 已完成公里数、课次和关键训练完成情况。

点击某天进入该次训练详情，不默认进入通用聊天。

### 7.3 训练方案详情

详情页展示：

- 目标赛事、距离、目标成绩和目标日期；
- 当前阶段、阶段目的和剩余周数；
- 各阶段路线和周跑量趋势；
- 每周基础结构、关键课和恢复边界；
- 可训练日、最长训练时间、伤病关注和场地等用户约束；
- 最近一次调整及原因；
- 方案版本历史。

## 8. 核心用户流程

### 8.1 首次创建训练方案

没有活跃方案时，训练页展示“生成我的训练方案”。系统优先使用已有数据预填最近四周跑量、训练频率、近期成绩、恢复状态、活跃目标和已知偏好，只询问无法从数据中获得的信息：

- 目标和目标日期；
- 每周可训练天数；
- 固定不可训练时间；
- 是否接受力量或交叉训练；
- 当前疼痛或医疗限制。

系统先生成草稿。用户查看目标、阶段、本周结构和安全边界后确认，形成第一个生效版本。未确认的草稿不得作为今日训练依据。

### 8.2 每日查看与执行

训练前，用户可查看详情、了解训练目的，或反馈时间不足、疲劳、疼痛、天气、场地和日程冲突。

训练后，系统同步并匹配实际运动；用户补充主观体感、疼痛和完成质量。系统据此判断完全完成、部分完成、替代完成或跳过。一次普通反馈不得自动重写整个训练周期。

### 8.3 调整今天或本周

用户提交约束后，系统返回结构化调整提案，必须包含：

- 用户反馈和使用的数据依据；
- 原安排与建议安排；
- 调整原因；
- 对本周其他训练、总量和关键课的影响；
- 风险、不确定性和安全提示。

用户可“确认调整”“继续讨论”或“保持原计划”。只有确认后才生成新方案版本并生效；拒绝不会改变当前方案。

### 8.4 每周复盘

每周结束后生成：

- 计划与实际完成情况；
- 周跑量、关键课和恢复趋势；
- 主动调整、数据缺失和无法匹配造成的偏差；
- 下一周建议及其理由。

下一周计划以提案形式出现，用户确认后生效。

### 8.5 方案级变化

目标日期、目标成绩、可训练天数长期变化，或用户连续生病、受伤、暂停备赛、完成比赛时，进入方案级调整，而不是只修改单日训练。

## 9. AI 与用户权限边界

AI 可以读取数据、解释安排、生成调整提案、匹配活动、生成周复盘和发现风险。

AI 不得：

- 未经用户确认修改已生效训练方案；
- 将暂未同步到活动直接判定为用户跳过训练；
- 修改历史计划来提高完成率；
- 在疼痛场景给出医疗诊断；
- 因一次普通指标波动重写整个周期。

## 10. 产品状态

### 10.1 训练方案

```text
draft → active → paused → active
                 └─────→ completed / archived
```

### 10.2 今日训练

```text
planned
├── adjusted
├── completed
├── partially_completed
├── substituted
├── skipped
└── unmatched
```

`unmatched` 表示暂未匹配到运动数据，不等于用户跳过训练。

### 10.3 调整提案

```text
pending
├── approved
├── rejected
├── superseded
└── expired
```

## 11. 异常与降级

- **没有目标**：生成滚动四周的一般训练方案。
- **没有平台数据**：允许创建草稿，但明确说明数据依据不足。
- **同步延迟**：展示“等待同步”，不判定跳过。
- **AI 服务不可用**：现有方案仍可查看和记录反馈，暂停生成新提案。
- **疼痛反馈**：优先暂停相关训练并提示进一步评估。
- **旅行或时区变化**：按用户当前本地日期展示，保留活动原始时间。
- **重复或多次训练**：匹配前去重，允许一个计划课次关联多个实际活动。
- **目标日期已过**：提示完成复盘、延期目标或归档方案。
- **并发修改**：旧版本提案不得覆盖新版本方案。

## 12. MVP 范围

### 12.1 必须包含

- 训练主界面和导航入口；
- 从实时活跃方案读取今日训练和本周安排；
- 无方案时的创建与确认流程；
- 时间不足、疲劳、疼痛、日程冲突四类快捷反馈；
- 调整前后差异、影响和原因；
- 用户确认后生效及版本记录；
- 运动数据自动匹配和训练后反馈；
- 移动端适配、结构化 API 和配套 MCP 能力。

### 12.2 暂不包含

- 拖拽式日历编辑；
- 多目标并行训练；
- 社交分享或真人教练协作；
- 自动写入外部平台训练日历；
- 复杂比赛预测模型；
- 完整伤病诊断或康复计划；
- 通用聊天历史作为训练页主体。

## 13. 交付阶段

1. **可感知**：训练主界面、实时方案、今日训练、本周安排和无方案状态。
2. **可交互**：训练反馈、调整提案、差异确认、版本管理和 MCP 能力。
3. **可自适应**：活动匹配、周复盘、执行偏差分析和下一周滚动提案。

正式发布至少包含“可感知”和“可交互”，否则没有解决无法交互式迭代的问题。

## 14. 验收标准

- 活跃方案变更后，无需重新生成日报即可在训练页看到最新内容。
- 没有方案时存在明确的创建入口，不展示空白指标。
- 今日训练同时包含可执行内容和安排原因。
- 四类快捷反馈都能产生包含原值、新值、原因和影响的提案。
- 未确认提案不会改变今日训练、本周安排或长期方案。
- 重复确认同一提案不会重复创建版本。
- 旧版本提案不能覆盖更新后的方案。
- 同步延迟和无法匹配不会被错误标记为跳过。
- AI 不可用时，已生效方案仍可完整查看。
- 疼痛反馈不会产生继续加量或提高强度的默认建议。
- 320px 宽度下关键信息和操作不重叠、不横向滚动。

## 15. 产品观察指标

先采集基线，不预设缺乏数据依据的目标值：

- 方案草稿确认率；
- 活跃方案用户的训练页访问频率；
- 今日训练查看率；
- 反馈到提案、提案到确认的转化；
- 提案确认、拒绝和继续讨论的分布；
- 计划训练与实际活动的匹配率；
- 调整后与未调整课次的完成情况差异；
- 用户确认后短期撤销或再次调整的比例；
- 疼痛场景未经确认自动改变方案的次数，要求为零。

## 16. 已确认决策

- 用户可见名称使用“训练方案”，不使用“运动大纲”。
- 训练主界面采用“今日训练 → 本周安排 → 长期方案”的信息优先级。
- 结构化页面是主要感知界面，对话用于解释和调整，不作为唯一入口。
- AI 只能创建调整提案，用户确认后新版本才生效。
- MVP 优先服务有明确跑步目标的用户，并兼容无比赛目标的滚动方案。

## 17. 文档维护

本文件是训练用户旅程的产品真相源。后续 UI 优化、交互调整、训练状态变化和相关 Bug 修复必须更新本文件的规范行为与验收标准；实现细节同步更新配套技术设计，不另建平行产品方案。
