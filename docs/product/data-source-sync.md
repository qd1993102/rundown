# 产品方案 — 数据源绑定与同步

> 版本: v2.6 · 日期: 2026-08-17
> 状态: Garmin、Coros 既有绑定与同步已实现；Huawei 新用户注册入口已于 2026-08-17 暂时下线，现有华为绑定用户同步不受影响；Coros 活动详情、原始 Hz 保留、单位归一化和 L2 聚合已有本地回放证据。`CanonicalActivityDetail` 到三消费者投影的统一强合同已确认，工程收敛与线上 Provider/ECS 存量重建验收待完成；Strava 个人用户活动同步为 Proposed
> 配套技术设计: [12-multi-platform.md](../design/12-multi-platform.md) · [13-sae-deployment.md](../design/13-sae-deployment.md)

## 1. 背景与问题

neurun 用户需要先绑定 Garmin、Coros 或 Strava（Huawei 新用户注册暂不可用），才能把活动与健康数据同步到自己的本地数据空间。
绑定成功必须意味着后续同步访问的是同一平台、同一账号和同一区域；不能出现登录校验通过，实际数据请求却发往
另一区域并误报 Token 失效的情况。

## 2. 产品目标

- 用户选择的数据源、Garmin 区域和账号在绑定、同步与重新绑定全过程保持一致。
- 单日和批量同步都只写入当前用户的数据空间，不生成或覆盖日报。
- 真正的认证失效给出重新绑定提示；网络、平台接口或程序错误不得伪装成认证失效。
- 同步失败保留可重试状态和明确原因，不写入错误用户 ID 或跨区域数据。
- 一个用户的慢同步不得阻塞其他页面、其他用户或基础设施存活检查。
- 单 ECS 在受控并发下接纳 100 个不同用户的同步请求，超出容量时快速返回可重试错误。
- 用户发起同步后不必维持长时间 HTTP 请求；页面可以独立查询任务状态和真实执行阶段。
- 在平台允许的范围内保留活动汇总、分段和路线负荷事实，并明确字段缺失原因，为训练内容分析提供可追溯输入。
- 同步完成后让训练方案和日报看到同一份日期覆盖与事实截止时间：它可以解锁日报生成、刷新能力档案和提示周复盘，但不自动生成日报、不自动激活或改写训练方案。

## 3. 范围与边界

### 3.1 本期范围

- Garmin 国际区 `garmin.com` 与中国区 `garmin.cn` 的账号绑定和数据同步。
- Garmin Access Token 到期后的无感刷新，以及刷新失败时的认证/临时错误区分。
- Strava 个人用户通过 Strava 官方 OAuth 2.0 授权连接活动数据；系统只申请并校验
  `activity:read_all`，用于读取该用户自己公开、关注者可见及“仅自己可见”的活动。授权页必须说明
  该范围和用途；用户拒绝或实际授予范围不足时不建立连接。
- Strava 的活动列表、活动详情、laps 与可用 streams（路线、心率、功率等）同步到当前用户隔离
  数据空间；`moving_time` 是训练实际时长，`elapsed_time` 保留为原始事实，不以暂停时间伪造训练时长。
- Strava webhook 处理新建、修改、删除、隐私变更与解除授权：回调只负责快速校验、持久化事件和
  调度后续处理，不在 2 秒内同步或调用 AI。
- Coros Training Hub 运动数据与 Mobile 睡眠数据采用两个独立授权入口、独立表单、独立状态和
  独立失败边界；任一授权失败不得撤销或误报另一条授权。
- Coros 两条授权都提供默认开启的自动鉴权选项；用户授权后保存各自经过认证加密的可重放凭据，
  在对应 Access Token 明确失效时自动刷新并只重试原请求一次。
- Huawei 的既有绑定和同步流程（新用户注册入口已于 2026-08-17 暂时下线）。
- 单日、批量同步及同步日历状态。
- Web 异步同步任务的发起、进度查询、刷新恢复和终态错误展示。
- Token 失效后的同平台重新绑定。
- 统一持久化训练识别所需的累计爬升、活动详情和 laps/splits；v1 已保留 Provider、标准单位和缺失值，逐字段原始来源与授权原因仍待 Provider 适配补齐。

### 3.2 非本期范围

- 不支持已绑定账号直接换到另一个运动平台。
- Strava v1 不读取或推断睡眠、HRV、静息心率、步数、压力、Body Battery 或训练准备度；这些维度
  在日报完整性中必须按 Strava 能力显示为未提供，不能填入零值或让用户误以为已经同步。
- Strava v1 不上传、编辑或删除 Strava 活动，不读取社交、俱乐部、排行榜或其他运动员数据，也不
  将 Strava 数据用于竞赛、排名或复刻 Strava 产品。
- Strava CLI OAuth、跨设备授权、多个运动平台同时绑定和自动导入历史文件不属于 v1；本期只提供
  已登录 neurun 用户在 Web 页面发起的浏览器授权。
- 不承诺第三方平台未授权或尚未映射的数据字段一定可用。
- 同步不隐式生成日报，也不调用 AI 教练。
- 同步不直接推进训练阶段、不确认调整提案；训练方案只能在后续显式启用、周复盘或用户确认流程中使用新增事实。
- 同步层不判定活动属于有氧、节奏、间歇或越野；第三方标签只作为后续分析证据。
- 不支持暂停、取消或自动恢复已经开始的平台请求；中断任务由用户确认后重试。
- 本期不引入 Redis、Celery 或跨 ECS 的分布式任务队列。

## 4. 用户流程与状态

1. 用户在首次设置中选择平台；Garmin 用户同时选择国际区或中国区；Strava 用户看到“连接 Strava”
   按钮、将读取的活动范围和“授权后可随时在 Strava 撤销”的说明，而不是账号密码输入框。
2. 系统完成登录并把 Token 保存到当前用户的隔离目录。
   - Coros 首次绑定只完成 Training Hub 运动数据授权；睡眠数据由用户从“我的”单独授权，
     不再在一次提交中串行申请两套 Token。
   - “我的”分别展示“运动数据授权”和“睡眠数据授权”的状态、自动鉴权状态和操作按钮；两个
     按钮不得指向无法区分目标的同一通用表单。
   - 运动数据授权页明确要求 **Coros Training Hub 登录账号**（邮箱或手机号）、密码和区域；
     首次授权默认选择“中国大陆”，用户可以改为账号实际所属的其他区域；重新授权从当前运动
     Token 继承区域。服务端收到未提供区域的运动授权请求时同样默认使用中国大陆，不得根据账号
     是否为纯数字猜测。
   - 睡眠数据授权页明确要求 **Coros App 登录邮箱** 和密码，说明这不是 neurun 登录邮箱；如果
     Coros 账号只绑定了手机号，用户需先在 Coros App 中绑定登录邮箱。页面继承当前运动授权区域，
     不得把中国区邮箱自动路由到欧洲区。
   - 点击“连接 Strava”后，浏览器跳到 Strava 的官方同意页；回调只在 state、当前 neurun 会话、
     返回的 athlete 标识和实际同意的 scope 都校验通过后才写入凭据并标记为 `active`。取消、过期
     state、scope 不足或交换 Token 失败都回到设置页并说明可重试原因，不创建半绑定用户。

### 4.1 异步任务与轮询流程

3. 用户选择同步范围并提交；服务端完成会话、参数、singleflight 和容量校验后创建任务。
4. `POST /api/sync` 立即返回 HTTP 202、不可猜测的 `task_id`、任务查询地址和初始
   `queued` 状态；202 只表示任务已可靠接纳，不表示平台数据已经同步成功。
5. 页面每 1 秒轮询任务查询接口，并展示排队、认证、同步指标、同步活动、备份和完成等真实阶段。
   Garmin 指标阶段展示 garmy 已处理的日期、指标和“已处理项 / 总项数”；Coros 活动阶段按平台
   已返回的分页记录数推进，健康阶段按已处理日期推进；Strava 只展示活动分页和已成功补齐的详情
   数量，不展示并不存在的健康同步阶段。明细随任务状态持久化，刷新后继续显示。
   第三方单次请求尚未返回、没有可信完成量时展示不确定进度，不按耗时伪造百分比。
6. 后台任务继续使用当前用户绑定的平台、区域和隔离目录执行；页面刷新后可用保存的 `task_id`
   恢复查询，不会重复发起同步。
7. 任务成功后刷新同步日历；失败时展示错误原因、是否可重试和建议动作。进程重启导致的未完成
   任务进入 `interrupted`，明确提示重新发起，不自动假定原任务仍在运行。
8. 同步由日报或训练页带入日期时，任务完成后保留来源与日期：日报来源返回
   `/reports?tab=daily&date=D` 并重新检查 readiness；训练来源返回同一训练周并提示能力/复盘事实已更新。
   两种返回都不自动生成日报或提交计划调整。

连接状态只有 `none`、`active`、`expired`：只有已确认的认证失效才能把 `active` 改为 `expired`；
普通网络错误、区域路由错误或第三方接口错误保持原连接状态，允许用户稍后重试。
Garmin Access Token 到期但 Refresh Token 仍有效时，后台必须自动续期并将新 Token 写回当前用户
目录，不能要求用户重新输入账号密码；Web 仍不保存 Garmin 明文密码。

### 4.2 Coros 双认证与自动鉴权

Coros Training Hub 与 Mobile 睡眠使用不同 Token，必须分别授权和刷新。两个授权表单都提供
“Token 失效后自动鉴权”选项，并在服务端已配置凭据加密密钥时默认开启；用户可在提交前取消，
也可之后在“我的”分别关闭。存量用户不从未知密码生成新凭据，需要进入对应授权页确认一次。
首次绑定用户虽然尚未绑定运动平台，但已经具备应用登录会话；页面必须使用只要求应用登录的
绑定能力接口查询安全加密能力，不能依赖仅面向已绑定用户的个人资料接口。能力查询成功且服务端
已配置密钥时，复选框默认勾选并允许用户取消；只有明确确认缺少密钥时才禁用。
首次绑定与重新授权页面都必须把勾选状态清晰渲染为原生复选框，不得继承账号输入框的内边距、
背景或边框而遮住勾号；每次进入 Coros 表单只执行一次能力初始化，避免重复请求覆盖用户看到的状态。

启用后，neurun 不保存高驰明文密码。Training Hub 的账号、区域和密码摘要，以及 Mobile 的加密
登录重放载荷，均视为“等同密码的敏感凭据”，分别经过服务端认证加密后写入当前用户隔离目录。
对应接口明确返回 `result=1019` 或等价认证失效时，后台只刷新该认证域、原子写回新 Token，并
只重试原请求一次；运动刷新不得改变睡眠状态，睡眠刷新失败也不得阻断运动、RHR 或 HRV 同步。

用户可以分别关闭运动或睡眠自动鉴权并立即删除对应加密凭据。关闭后不影响该域当前 Access Token；
下次真正失效时只提示重新授权对应数据域。高驰明确拒绝凭据时删除该域不可用凭据；超时、限流和
5xx 保留凭据与既有状态，提示稍后重试。服务端缺少加密密钥时仍允许人工授权，但两个自动鉴权
开关必须禁用并解释原因，不得以明文或仅编码形式降级保存。

## 5. 交互规则

- Garmin 中国区绑定后，所有 profile、活动和健康接口都必须继续访问 `garmin.cn`。
- 已绑定用户不得因服务级默认平台或默认 Garmin 区域而切换数据源。
- Coros “我的”页必须使用含义不同的两个按钮：“授权/重新授权运动数据”和“授权/重新授权睡眠
  数据”；前者只进入 Training Hub 表单，后者只进入 Mobile 表单。
- 两个表单都隐藏平台切换并固定为当前用户的 Coros，但标题、账号字段说明、区域规则、提交接口和
  成功提示必须按认证域区分。不得再用一个提交同时完成运动与睡眠授权。
- Coros 运动认证的页面与 API 默认区域统一为中国大陆（`cn`）；这只是初始默认值，不覆盖用户
  显式选择的欧洲、美国或中国大陆以外亚洲区域，也不改变重新授权时从现有 Token 继承的区域。
- 睡眠授权只有在 Mobile token 或可刷新凭据已实际取得时才成功；失败时页面停留并展示高驰返回的
  脱敏业务错误码或网络原因，已有运动授权保持不变。
- Coros 重新授权成功后进入同步页，普通批量同步即可合并补齐历史睡眠，不要求删除活动或
  强制覆盖已有数据。
- Coros 运动和睡眠表单的自动鉴权选项在服务端支持安全加密时默认勾选；页面说明会保存加密的
  等同密码凭据，并提供分别关闭和删除凭据的入口。默认开启不等于绕过授权：用户仍需在对应表单
  提交一次正确凭据。
- 自动鉴权能力探测只要求有效的 neurun 应用会话，不要求用户已经绑定运动平台；首次绑定页面
  不得因为个人资料接口的绑定门禁返回 401 而把可用能力误判为不可用。
- 首次绑定和两个重新授权表单必须明确显示自动鉴权的已勾选状态，且同一次页面初始化只发起一次
  能力探测；通用文本输入框样式不得覆盖复选框的尺寸、内边距和勾选色。
- 未配置服务端加密密钥时，人工授权本身仍可成功，但自动鉴权开关必须禁用并明确提示当前部署
  不支持安全留存凭据，响应不得把这一配置问题描述为账号密码错误。
- 同步返回 HTTP 401 时必须表示当前凭据确实不可用，并提示重新绑定原平台。
- Garmin 自动刷新只有在 Refresh Token 已过期、被撤销，或刷新接口明确返回 401/403 时才进入
  重新绑定；超时、限流、Garmin 5xx、响应格式异常或 profile 临时不可用保持 `active` 并允许重试。
- 非认证错误返回对应失败原因，不要求用户无意义地重复输入账号密码。
- 同步失败不得使用 `user_id=0` 继续写入，也不得把数据写到其他用户目录。
- 同一用户已有同步执行或排队时，重复请求返回 HTTP 409 和
  `sync_in_progress`，不再发起第二份平台请求。
- 全局已达 100 个不同用户同步时，新请求返回 HTTP 503 和
  `sync_capacity_exceeded`，明确提示稍后重试。
- 同步排队或调用第三方平台时，`GET|HEAD /healthz` 仍必须及时返回；
  慢上游不得占用 Web 事件循环。
- 每次同步结束后必须释放 SQLite engine、HTTP Session 和其他可关闭资源；
  过期 MFA 中间状态不得无限保留连接对象。
- 同一用户已有任务时，重复发起仍返回 HTTP 409，但响应必须携带现有
  `task_id` 和查询地址，让页面恢复轮询而不是创建第二份任务。
- 任务只能被创建它的登录用户查询；其他用户访问统一返回 404，响应和日志都不得
  暴露 Cookie、API Key、平台 Token、邮箱或第三方原始响应。
- 轮询响应使用 `Cache-Control: no-store`，运行中建议客户端 1 秒后重试；任务进入
  `succeeded`、`failed` 或 `interrupted` 后停止轮询。
- 页面必须区分“已接纳”和“同步成功”，关闭页面或网络断开不取消已接纳任务。
- 阶段总进度与阶段内明细必须分开表达；逐项总数不得被渲染成同等数量的顶层阶段块。
- 原始平台训练负荷、活动类型和活动名称必须保持可追溯；后续派生分类或派生负荷不得覆盖原值。
- Strava 连接页必须使用官方“Connect with Strava”品牌资产，并在展示来源活动时以可访问文字与
  链接标注“View on Strava”；不得把 neurun 的训练判断描述为 Strava 的结论。
- Strava 实际同意的 scope 必须随 Token 保存并在“我的”展示。若没有 `activity:read_all`，不得
  把缺少“仅自己可见”活动伪装成同步完成；页面应提示重新授权。
- 收到 Strava 解除授权 webhook 或 Token 刷新明确返回认证失败时，立即停止后续 Strava 拉取，删除
  本地 OAuth 凭据并把连接标记为 `expired`；用户可重新通过官方 OAuth 绑定同一平台。
- 收到活动删除或隐私改为不可访问的 webhook 后，后续异步任务必须让本地活动的可用范围与 Strava
  当前授权一致；Webhook 重复送达、乱序或未知 athlete 不得导致跨用户删除或同步。

### 5.1 训练识别数据基础

- **统一模型边界**：Provider 原始详情必须先转换为唯一的
  `CanonicalActivityDetail`，再确定性派生 `SessionSummaryFacts`；按本地日期聚合为
  `TrainingDayFact` 后生成同版本的确定性 `TrainingDayAnalysis`，日报、周复盘和方案草稿只读取从
  这些事实生成的 `ConsumerProjection`；周复盘先固化 `WeeklyPrerequisiteManifest` 再做周聚合。
  除 Provider Adapter 外，任何存储、报告、训练或 AI 输入层
  不得出现 Garmin/Coros/Huawei/Strava 原始字段分支。
- **值与缺口**：合同中每个可缺事实只能是带标准单位的已知值，或带
  稳定原因、影响范围和 evidence 引用的显式 gap。真实 `0` 是已知值；`null`、
  空字符串、空对象或默认 `0` 都不能代表未提供、未授权、未映射或单位未确认。
- **版本与输入指纹**：`schema_version` 表示结构合同，`detail_hash` 表示规范化
  活动详情的输入指纹，`fact_version` 表示包含 schema、规则版本和输入引用的
  派生事实内容身份。三者不得互相替代：详情未变但 schema/规则变化仍会
  产生新 `fact_version`；只有 `detail_hash` 不能证明摘要事实未变。
- **标准单位**：距离为 `m`，时长为 `s`，配速为 `s/km`，心率为 `bpm`，步频为
  `spm`，步幅为 `cm`，海拔/爬升为 `m`，功率为 `W`，热量为 `kcal`，比率为
  `ratio`，百分比为 `percent`。Provider 训练负荷不具备通用单位，必须保留
  Provider 命名空间，不得直接横跨平台比较。
- **事实证据**：每个已知值至少引用一条结构化 evidence，定位到 Provider、
  来源记录、原始字段、观测/截止时间、转换规则、标准值与单位；代理值还必须
  记录 `basis`。自然语言解释只是 evidence 的投影，不能成为唯一事实来源。
- 活动汇总至少表达字段值、标准单位、来源 Provider 和“真实零值 / 未提供 / 未授权 / 尚未映射”的区别。
- laps/splits 在 Provider 支持时按原始顺序保存，并保留工作、恢复、热身、放松等平台分段标签；未知标签保留原值，不强行映射。
- **Coros 原始详情与 Hz 状态**：Coros 活动详情使用自建请求保留 `lapList`、`graphList`、
  `frequencyList` 和 `gpsLightDuration` 的原始响应。原始 Hz 数组写入 `detail_json` 只表示“可回放”，
  不表示已经形成逐点分析；只有完成字段解析、单位归一化、有效样本校验和聚合后才能把摘要标记为
  `L2`。未解析、单位未确认或解析失败时保持 `L1`/`L0`，并记录 `hz_unparsed`、
  `unit_unverified` 或具体失败原因，不得以原始数组存在冒充逐秒配速或心率能力。
- **Coros 单位归一化**：当前 Training Hub 详情协议中，活动和 lap 的 `distance` 以 `1/100 m`
  保存，`workoutTime`、`totalTime`、lap 的 `time`/`totalLength` 以 `1/100 s` 保存；归一化后分别
  写为米和秒；`calories`/`calorie` 以 `1/1000 kcal` 保存，归一化为 kcal。`avgPace` 直接按 `sec/km`，`avgHr` 按 `bpm`，`avgCadence` 按 `spm`，
  `avgStrideLength` 按 `cm` 保存。原始值、转换因子和目标单位必须进入 evidence；未知运动类型或
  响应版本未通过夹具验证时不得套用转换，必须标记 `unit_unverified`。
- **Coros 分段权威层级**：`lapList[].lapItemList[]` 是首选叶子分段；父 lap 只用于分组和校验，
  不得与其子项重复累计。只有父 lap 没有有效子项时才退回父 lap；活动 `summary` 只提供总量，
  不能作为额外分段。按 `lapIndex`、起止时间和累计距离去重后，归一化分段距离合计与活动汇总
  距离的比值必须位于 `[0.85, 1.15]` 才能输出分段距离、时长或“每公里”结论。超出范围时保留
  可独立验证的强度序列，标记 `quantity_unreliable`，不输出量结论。只有平台明确标记为公里 lap，
  或归一化距离在 `1000 +/- 20 m` 且门禁通过的分段，才可称为“每公里分段”；其他统一称“平台分段”。
- **Coros 平台自算乳酸阈值**：`/analyse/query` 返回的 `lthr`（乳酸阈值心率 bpm）与 `ltsp`（乳酸阈值配速 s/km）随每日健康数据解析并写入 `daily_health_metrics.lthr/ltsp`，训练内容识别按“用户档案显式阈值 > 平台 lthr/ltsp > 档案推导”自动采用（取目标日及之前最近一条）。
- 累计爬升统一使用米，不能用起终点海拔差替代；有逐点或逐段海拔时同时保留可用于计算坡度和连续爬坡段的事实。
- 同步完成只表示已保存当前 Provider 可获得的数据，不表示训练内容已经识别，也不表示数据足以作出高置信度判断。
- 后续补齐活动详情或修正字段时必须允许重新分析，不要求用户删除活动或重新生成全部历史日报。

### 5.2 单日同步日期选择

单日同步以同步日历为主要日期上下文，单日卡必须把“本次同步目标”的完整日期、星期和已知同步状态
清楚分层展示。用户优先点击日历日期；也可以使用前一天 / 后一天、昨天 / 今天快捷操作，或在可见的
“修改日期”日期字段中精确选择。所有入口写入同一日期状态，自动更新日历高亮、目标摘要、同步按钮和
屏幕阅读器文本。未来日期不可选。原生日期字段是明确的精确修改入口，不以不可见覆盖层承担当前状态表达。
来自日报的 `date=D` 仍优先预选 `D`、切换日历月份并锚定单日同步卡。

## 6. 验收标准

1. Garmin 国际区和中国区账号都能在绑定后使用同一区域完成 profile、活动及健康数据请求。
2. 中国区 Token 不会被发送到国际区 API，国际区 Token 也不会被发送到中国区 API。
3. 有效中国区 Token 发起单日或批量同步时不会误报“Garmin 认证失败”。
4. 真正的 Token 失效仍返回 HTTP 401、标记连接 `expired` 并提供重新绑定入口。
5. 非认证异常不会把连接误标为 `expired`。
6. 同步只更新当前用户 SQLite 和同步状态，不创建或覆盖日报。
7. “我的”页同时出现运动与睡眠操作时，两个按钮的文案、目标 URL 和表单标题均可区分，不再
   指向同一个无作用域入口。
8. 运动授权页明确展示 Training Hub 账号要求和区域选择；睡眠授权页明确展示 Coros App 登录邮箱
   要求并继承已保存区域。首次运动授权默认选择中国大陆，省略区域的 API 请求也按中国大陆处理；
   用户显式选择其他区域时保持该选择。中国区邮箱不会再自动选择欧洲区。
9. Coros Mobile 授权失败时，运动绑定仍保持可用；Training Hub 授权失败也不删除有效 Mobile
   凭据。两个页面分别展示对应失败原因，不包含账号密码、密码摘要、重放载荷或 token。
10. 受控慢同步执行期间，`/healthz` 不被同步任务的阻塞时间拖延。
11. 同一用户的两份同步不会并行写入同一 SQLite，重复请求稳定返回 409。
12. 默认配置下同时执行上限为 4，全局接纳上限为 100；第 101 个不同用户返回 503。
13. 100 用户合成同步压测无串库、无写入失败，FD 在任务结束和资源关闭后回落。

### 6.1 异步任务补充验收标准

14. 合法同步请求在完成任务持久化和调度接纳后快速返回 HTTP 202，不等待 Garmin、Coros 或
    Huawei 完成；响应包含 `task_id`、`status=queued` 和任务查询地址。
15. 轮询接口只返回当前用户的任务，稳定表达 `queued`、`running`、`succeeded`、`failed`、
    `interrupted` 五种状态及当前阶段、更新时间、范围和结构化错误。
16. 页面刷新、短暂断网或一次轮询失败不会重复提交任务；恢复后继续查询同一个 `task_id`。
17. 同用户重复提交返回 409 并附带现有任务信息；容量已满仍返回 503，二者均不创建孤儿任务。
18. 任务失败不会把 HTTP 轮询本身伪装成 500；查询成功时返回 200，由任务 `status`、`error.code`、
    `error.retryable` 和 `error.action` 表达业务终态。
19. 服务重启后，旧实例遗留的 `queued/running` 任务变为 `interrupted`，日历与任务状态不显示
    永久“同步中”，用户可以安全重试。
20. 进度展示以真实阶段或 Provider 明确上报的完成量为依据；不能仅按运行时间生成虚假百分比。
    Garmin 指标同步期间，任务更新时间应随已处理日期/指标推进，并返回可恢复的逐项计数；页面刷新后
    继续显示同一任务的最近真实进度，而不是长期停留在阶段 `2 / 4`。
    Coros 活动分页返回后按真实记录数推进，健康同步按日期推进；活动或 Mobile 睡眠请求尚未返回时
    不增加计数。Coros 逐项快照同样可由刷新后的轮询恢复。
21. 任务终态、资源释放和 SQLite 备份完成顺序可验证；成功不得早于备份完成，失败路径也不得
    泄漏 Provider Session、engine 或后台协程异常。
22. Garmin Access Token 过期而 Refresh Token 有效时，同步自动刷新并继续执行，不调用账号密码
    登录，也不把连接标记为 `expired`。
23. 自动刷新成功后 OAuth2 Token 持久化到当前用户目录，服务重启后继续使用新 Token。
24. Garmin profile、刷新或数据接口的超时、429、5xx 和其他非认证异常返回可重试失败，用户连接
    保持 `active`；只有明确的 401/403 或不可再刷新的凭据才提示重新绑定。

### 6.2 Coros 双认证与自动鉴权验收标准

1. 首次绑定 Coros 只请求 Training Hub；睡眠授权只能由独立 Mobile 表单触发，两次提交和响应互不
   冒充成功。
2. 服务端具备加密密钥时，两个表单的自动鉴权选项默认勾选；用户取消任一选项后不得生成该域的
   重登凭据。首次绑定且尚无 active 数据源的用户也能取得该默认值。缺少密钥时选项禁用且原因
   可见，人工授权仍可完成；未登录用户不能读取绑定能力。
3. 开启后，用户目录和日志中都不存在明文密码、裸密码摘要或未加密的可重放登录请求；两个域的
   持久化文件只有经过认证加密的密文，权限为 `0600`，解密密钥不与用户数据一同保存。
4. Training Hub 与 Mobile 分别在 `result=1019` 或等价认证失效时触发一次自动鉴权；成功后只写回
   对应 Access Token，原请求最多重试一次，不产生无限重试。
5. 同一用户同一认证域的并发请求只允许一次刷新；两个域互不共用锁、凭据或失败状态。
6. 高驰明确拒绝已保存凭据时只删除对应域凭据并更新对应状态；临时网络、限流或 5xx 不删除凭据，
   不把另一域标记为失效。
7. 用户分别关闭自动鉴权后，对应加密凭据立即删除，当前 Access Token 保持可用；后续失效时只要求
   人工授权对应数据域。

### 6.3 训练识别数据基础验收标准

1. 各 Provider 的累计爬升统一为米，缺失与真实零爬升可以区分，原始字段和值可追溯。
2. Provider 支持 laps/splits 时，同步后可以按顺序读取分段时长、距离、心率、配速或功率以及原始分段标签；不支持时返回明确的数据质量状态。
3. 活动详情晚于活动汇总到达时可以幂等补齐，并触发对应派生分析失效或重算，不覆盖其他用户数据。
4. 同步过程不生成有氧、节奏、间歇或越野结论，也不修改平台原始训练负荷。
5. 用户未生成任何日报时，已同步的原始活动仍可供训练内容分析读取。
6. Coros 原始 `frequencyList` 已入库但尚未完成规范化解析时，摘要最高只能为 `L1`；响应必须显式
   标记 Hz 未解析，不能输出逐秒配速、逐秒心率或 L2 精度描述。
7. Coros 8.14126 km / 2582.45 s 夹具归一化后必须得到约 `8141.26 m`、`2582.45 s`；
   `avgPace/avgHr/avgCadence/avgStrideLength` 分别以 `sec/km`、`bpm`、`spm`、`cm` 输出。
8. `lapItemList` 有有效子项时，父 lap 不参与距离和时长求和；去重后的归一化分段距离比值超出
   `[0.85, 1.15]` 时，不得输出每公里距离、分段时长或依赖其计算的量结论。
9. 重同步或解析规则升级后，只重算受影响活动的分段与摘要；原始 `detail_json` 保留，其他用户和
   已归档报告引用的历史摘要版本不被后台静默改写。
10. 新写入的 `CanonicalActivityDetail` 和 `SessionSummaryFacts` 都必须带非空
    `schema_version`；后者同时带 `detail_hash`、`fact_version`、规则版本和来源 evidence。
11. 相同规范化输入、schema 和规则生成字节级相同的 `fact_version`；任一业务事实、
    schema 或规则版本变化都产生新 `fact_version`，仅计算时间变化不影响版本。
12. `L0` 只证明可用汇总量；`L1` 必须包含通过数量门禁的有序分段；`L2`
    必须包含完成单位归一化、无效点过滤和确定性聚合的高频样本。`L2` 隐含
    `L1` 和 `L0`，但任一单字段仍必须通过自身 `ValueOrGap` 表达可用性。
13. 存量无 schema/事实版本记录不得被当作新合同记录回写；有原始详情时旁路
    生成新版本，无法重算时以 `legacy_unversioned` gap 降级读取。已归档报告
    继续锁定当时引用，不得被迁移后的当前版本反向改写。
14. Garmin、Coros 及后续 Provider 的详情经 Adapter 后，消费层只接收
    `CanonicalActivityDetail -> SessionSummaryFacts -> TrainingDayFact -> TrainingDayAnalysis`
    的统一链路；日报、周复盘和方案草稿不得按 Provider 分别适配距离、平均配速、分段、心率、步频、
    步幅或质量课规则。

### 6.4 Strava 个人用户活动同步验收标准（Proposed）

1. 未绑定用户只能从 neurun 设置页开始 OAuth；授权请求含不可预测、一次性且有有效期的 state，
   回调不能把一个用户的授权写入另一个用户目录。
2. 用户取消授权、回调 state 无效、Token 交换失败或没有授予 `activity:read_all` 时，页面给出
   可操作原因且用户保持未绑定；不得保存授权码、access token、refresh token 或 client secret。
3. 有效授权只把当前 athlete 的 ID、实际 scope 和 OAuth 凭据写入当前用户私有目录；页面与日志
   均不得显示 token、授权码或 client secret。access token 过期后使用最新 refresh token 刷新，
   刷新成功时原子替换两种 token。
4. 同步至少保存活动 ID、名称、运动类型、带时区的开始时间、`moving_time`、距离、平均/最大心率、
   卡路里、累计爬升和原始来源；详情、laps 与 streams 可用时幂等补齐，缺失时记录质量原因而非零值。
5. Strava 的每日健康维度在同步日历、日报完整性与训练事实中均明确为未提供；系统不生成睡眠、HRV、
   静息心率或恢复结论来填补该缺口。
6. webhook 验证请求仅在 verify token 正确时返回 challenge；POST 在两秒内确认接收，并把活动新建、
   修改、删除、隐私变化和 athlete 解除授权异步处理。重复或乱序事件保持幂等。
7. 解除授权或本地“断开 Strava”后，系统不再请求 Strava；本地 OAuth 凭据立即删除，连接状态变为
   `expired`，同时保留已同步活动是否删除的显式用户选择，不能静默改变训练历史。
8. 单个用户全量回填会遵守 Strava 响应中的限流头；429 或短暂 5xx 作为可重试任务失败，不把连接
   标为失效，也不持续轮询代替 webhook。
