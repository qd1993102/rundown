# review-training-plan 轻量上线验收

- **适用范围**：训练方案草稿审阅、启用入口审阅、周执行复盘。
- **目标**：确认方案审阅不会把可执行草稿误判为失败，并能用最少的运营数据发现计划—执行偏差、安全确认和规范化异常。
- **数据边界**：只使用已存在的方案/周复盘结果和用户确认动作；不新增群发、活动或人工跟进流程。

## 验收前提

1. 仅统计有生效方案且计划覆盖窗口完整的自然周。`sync_state=unknown` 或覆盖不足的周进入“数据不足”，不计入一致率分母。
2. 以服务端落盘的方案候选、启用/调整确认结果和周复盘结果为准；页面展示、AI 文案和客户端重试不作为事实源。
3. 指标先建立首个完整自然周基线，不预设行业目标值。上线阻断条件只有：数据无法区分“无数据”和“未完成”、安全提示确认状态丢失、或确认动作与实际生效版本不一致。

## 四项最小观察指标

### 1. 周累计一致率

在合格周集合中，满足以下条件的周占比：

```text
session_completion_ratio ∈ [0.80, 1.20]
且 volume_completion_ratio ∈ [0.80, 1.20]
```

其中两个比率直接取 `plan_execution_summary`：

```text
session_completion_ratio = completed_sessions / planned_sessions
volume_completion_ratio  = completed_km / target_km
```

分母为合格周数；`planned_sessions=0` 或 `target_km=0` 的周只报原始值，不强行计入一致/不一致。运营看板同时保留计划公里、完成公里、完成课次和 `sync_coverage`，避免把同步缺口误解为漏训。

### 2. reconciliation adjustments

每个训练方案候选/重规划提案记录：

- `adjustments` 为空：无确定性规范化；
- `adjustments` 非空：记为一次 reconciliation adjustment，并保留原文、候选类型（草稿或重规划）和方案版本；
- 报告 adjustment rate（有 adjustment 的候选数 / 合格候选总数）及前五种重复原因。不要把 adjustment 直接判定为质量事故，它表示系统为补齐 Workout Steps v2 或字段一致性做过确定性处理。

### 3. `entry_review` / `execution_review` 决策分布

按周和方案版本分别统计决策，不合并两个阶段：

| 事件 | 最小决策枚举 | 说明 |
| --- | --- | --- |
| `entry_review` | `confirm`、`edit`、`defer`、`reject`、`unknown` | 启用预览后的入口动作；没有动作的草稿不算 `reject` |
| `execution_review` | `keep`、`local_adjustment`、`scheme_revision`、`insufficient_data`、`unknown` | 取周复盘的确定性 recommendation/progression decision；未知同步必须保留为 `insufficient_data` |

验收只检查分布可解释、事件去重（同一用户/方案/周/动作一次）以及确认后状态是否落盘；不为某个决策比例设置硬目标。

### 4. safety_hold 确认率

```text
safety_hold 确认率 = 已确认并继续采用的 safety_hold 数 /
                    需要用户确认的 safety_hold 数
```

分母只包含候选中存在 `review.safety_hold` 且确实进入确认界面的记录；`pending`、`dismissed`、`expired` 单独计数，不能当作未触达或确认失败。确认动作必须关联 `preview_id`/`plan_id`/方案版本；没有关联 ID 的动作计入数据质量异常。

## 上线当天清单

- 抽样检查 3 个普通审阅候选：可预览、可暂存，未因一般 `review.items` 阻断。
- 抽样检查 1 个含 `safety_hold` 候选：未确认前不生效，确认后只生效一次且可追溯。
- 抽样检查 1 个有 `adjustments` 的候选：页面能解释规范化内容，原始候选仍可追溯。
- 复盘首个完整自然周：导出四项指标的原始分子/分母、`sync_state`、方案版本和缺失字段数。
- 若事件未采集或字段缺失，标记“验收阻塞/待补采集”，不补猜比例、不开展人工召回。

## 异常处理

只做三种动作：等待下一个完整周、重试/补齐只读统计、升级为数据契约问题。发现安全确认丢失或错误生效时，暂停宣布通过并保留当前方案状态，交由开发核对落盘与幂等链路。

## 草稿生成前补充信息窗口（轻量）

补充信息是用户在提交草稿生成前提供的可选上下文，不替代已同步的结构化事实、目标约束或安全确认。窗口应保持单次、短文本、可跳过；空提交必须等价于“未提供补充信息”，不得把用户留空解释为拒绝生成。

### 最小运营指标

仅在核心草稿生成请求已通过既有 readiness/准入的样本中统计，首个完整自然周建立基线，不预设行业目标值：

```text
输入完成率 = 提交了明确结束动作（填写并提交或明确跳过）的窗口数 /
             展示补充信息窗口的草稿生成请求数

有效使用率 = 被服务端接受、写入本次生成上下文且通过长度/格式校验的非空输入数 /
             补充信息窗口提交数（空值、明确跳过单独统计）

补充信息失败率 = 因补充信息解析、校验或持久化失败的请求数 /
                 补充信息窗口提交数

补充信息阻塞率 = 因补充信息失败、空值或超时而未进入草稿生成的请求数 /
                 已通过核心准入且展示补充信息窗口的请求数
```

运营看板至少分开记录 `submitted`、`skipped`、`empty`、`accepted`、`invalid`、`persist_failed`、`timeout` 和 `generation_started`。同一用户重复点击只计一次窗口提交；请求没有展示窗口（旧客户端或明确不适用）不计入完成率分母。

### 验收规则

1. 填写有效补充信息后，草稿生成使用该输入并能在任务/草稿审计记录中关联本次 `request_id`；不要求在用户界面回显完整原文。
2. 用户明确跳过或提交空值时，仍应启动草稿生成，并在上下文中记录 `no_additional_context`；不计入有效使用，但不能计为失败。
3. 输入超长、格式不合法或安全过滤失败时，显示可操作提示并允许清空后继续；若核心事实满足生成条件，必须自动按无补充信息路径继续，不能静默丢失为“已使用”。
4. 补充信息存储或读取异常时，保留草稿生成主链路；结果标记 `supplement_unavailable`，并记录失败分类供排查。只有核心事实或准入失败才允许阻断生成。
5. AI 处理补充信息失败不得改变上述不阻断规则；确定性草稿或既有 AI fallback 仍按原流程产出，不能把补充信息失败归因于“无草稿”。

### 上线抽样与告警

- 抽样 3 个有效输入、2 个明确跳过、1 个空提交、1 个超长/非法输入，确认均有清晰终态；后四类不得导致核心准入通过后的生成阻塞。
- 复核一条 `accepted` 和一条 `supplement_unavailable` 记录：上下文关联、脱敏日志和草稿生成终态可追溯。
- 首周每天查看完成率、有效使用率、失败分类和阻塞率；阻塞率出现任何可复现的非零样本即标记验收阻塞，先修复或降级为无补充信息路径。
- 不因有效使用率偏低自动增加强制输入或召回；先区分用户主动跳过、空值、校验失败和埋点缺失。
