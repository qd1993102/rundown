# 用户关联数据 TAR 导出治理与上线准备

- **状态**：脱敏本地脚本 MVP 已实现；生产交付、审批、审计和自动清理治理仍未上线。
- **适用范围**：根据人工提供的用户线索定位一个账号，并为受理的数据访问、迁移或故障支持请求生成单用户数据包。
- **结论**：独立脚本允许使用当前昵称做精确匹配；唯一匹配时锁定单一内部账号键，重名必须用邮箱消歧，不能自动选择。该脚本只生成脱敏本地包，不是完整灾备或对外交付系统。
- **数据范围**：本文只定义拟上线能力的运营、合规和可观测性约束。仓库未提供生产数据、权限系统、审计存储或历史指标，所有阈值和保留期均标为待决，不作行业基准推断。

当前实现：`scripts/export_user_data.py` 只包含显式 allowlist 数据，永久排除 Token、API Key、密码哈希、Cookie、邀请码、配置、日志、源码和其他用户数据；输出文件由管理员在受控目录中自行传输和清理。

## 1. 目标、非目标与发布门禁

运营目标是在有正当事由、最小数据和可回放审计的前提下，交付一个可验证归属的用户数据包，并避免令牌、会话标识、密码哈希和其他用户数据越界。

非目标：批量导出、按昵称模糊匹配后自动选择、营销触达、自动召回、将数据包交给第三方、通过导出修复或回写用户数据。运营不得自行执行外部发布、群发或数据修改。

上线阻断条件如下，任一未满足则能力不得开放：

1. 请求只提供昵称，或候选账号多于一个；
2. 无可验证的请求主体、授权依据、审批人和用途；
3. 未实现操作人鉴权、最小权限和不可篡改的审计记录；
4. 压缩包包含凭据、认证材料、密码哈希、会话标识、邀请码或其他用户的数据；
5. 没有加密传输/交付方式、到期清理和失败终态；
6. 文件命名含昵称、邮箱、完整 `api_key` 或其他直接标识符；
7. 无法采集本文第 6 节的最小事件字段，或未完成第 8 节验收。

## 2. 账号定位与用户分层

仓库事实：登录邮箱是唯一性校验字段，昵称允许重复且可修改；`UserManager` 提供邮箱和 `api_key` 查询，不提供昵称查询。因此昵称重复、空白、改名及同形字符均为预期情况，不能按昵称自动挑选用户。

| 阶段 | 允许输入/动作 | 必须结果 | 禁止动作 |
| --- | --- | --- | --- |
| 受理 | 工单号、请求类型、昵称线索 | 创建 `request_id`，标记为待核验 | 以昵称生成文件或读取数据 |
| 身份核验 | 经认证的本人会话，或经审批的支持工单；邮箱可作受控二次比对 | 唯一且稳定的 `api_key`、授权范围、审批记录 | 将邮箱/昵称写入文件名、日志或运营报表 |
| 范围确认 | 导出用途、类别、接收方、失效时间 | 最小数据清单和 `export_id` | 默认选择“所有文件” |
| 生成与交付 | 具备导出权限的操作人或受控服务身份 | 已校验的清单、校验和、审计事件 | 复用登录 Cookie、扩大为多用户 |
| 清理与关闭 | 到期、下载完成或取消 | 删除工作副本并记录终态 | 静默保留或自动再次发送 |

建议仅按请求目的分层，不从运动表现、活跃度或健康数据派生运营分层：`subject_access`（本人数据访问）、`support_diagnosis`（最小故障排查）、`approved_migration`（经批准迁移）、`security_forensics`（紧急取证）。前三类默认不含密钥；第四类必须单独走书面 break-glass 审批，不能由普通 TAR 导出入口承载。

## 3. 数据范围、脱敏与归档

默认“支持/访问数据包”必须是最小化导出，而不是目录复制。实现前应建立可测试的 allowlist 和 manifest；未知文件、符号链接、父目录跳转、其他 `api_key` 路径和全局文件一律失败关闭。

| 数据类别 | 默认处理 | 说明 |
| --- | --- | --- |
| 用户资料 JSON | 仅输出显式 allowlist 后的必要字段，或使用导出专用元数据 | 原文件含邮箱、`password_hash`、平台账号字段和 `api_key`，不得原样打包 |
| `data.db` | 仅在已批准目的下纳入；交付前确认库中不含跨用户数据 | 可能含运动、健康和训练事实，属于高敏感个人数据 |
| `memory/`、日报、周复盘、方案 | 仅在请求范围包含时纳入 | 可能含健康、训练和 AI 结论；不得在日志中打印正文 |
| `sync-tasks.json` | 默认排除，需排障时提取脱敏副本 | 任务错误可能携带外部账号或实现细节 |
| `tokens/`、`huawei-tokens/` | 永久排除 | OAuth/access/refresh token 或平台凭据，禁止进入普通包 |
| Cookie、环境变量、配置、邀请码、全局 `users/`、`backup/` | 永久排除 | 可能影响其他用户或服务控制面 |

所有临时副本、manifest 和 TAR 都必须在受限目录创建，权限由技术方案定义且需经安全审查；不得写入共享 `/tmp`、仓库、浏览器下载目录或工单附件。TAR 本身不提供保密性，交付必须使用经批准的加密传输和受控下载机制。若无此机制，生成后不得交付。

保留规则尚无已确认时长。上线前主 Agent/数据负责人必须确认：请求记录、审计日志、可下载包、失败的临时文件和 break-glass 证据各自的保留期、属主、清理责任和法律留置例外。到期删除应记录删除结果和时间，不记录文件内容；清理失败必须告警并停止扩大发放。

## 4. 权限、审批与审计

导出动作至少需分离“请求受理/核验”“审批”“执行/交付”三项职责；同一人兼任需在紧急路径中明确记录理由和二次复核人。服务端不得把现有 `api_key` Cookie 或管理员 MCP 开关等同于导出授权。

每次请求在生成前必须绑定：`request_id`、`export_id`、稳定目标 `api_key`、请求类型、最小数据类别、授权依据、审批人、执行人、接收方类别、创建/到期时间和发布版本。审计事件至少覆盖 `requested`、`identity_verified`、`approved`、`started`、`validated`、`delivered`、`expired_deleted`、`failed`、`cancelled`；记录前后状态、失败分类、重试序号、清单摘要、字节数和校验和。

审计和指标中不得写入昵称、邮箱、完整 `api_key`、文件路径、TAR 内容、报告正文、运动原始序列、密码哈希、Token、Cookie、Authorization 或密钥。需要关联回放时，使用受控系统内的 `request_id`/`export_id`；若需用户关联，由受权限保护的映射表完成，不进入运营导出。

## 5. 文件命名、完整性与交付

推荐命名：`neurun-user-export-<export_id>-<created_utc>.tar`；`export_id` 应为不可枚举的随机标识，时间采用 UTC 的 `YYYYMMDDTHHMMSSZ`。不得使用昵称、邮箱、完整/截断 `api_key`、工单正文或健康信息。压缩格式、是否加密以及密码/密钥交付渠道须由技术和安全负责人明确；在该决定前不得宣称 TAR 已受保护。

包内仅包含 allowlist 文件和机器可读 `manifest.json`。manifest 至少列出格式版本、`export_id`、创建时间、数据类别、每个条目的相对安全路径、大小、SHA-256 和脱敏规则版本；不含直接标识符或敏感字段值。生成后必须在交付前重新读取并验证：成员无重复、无绝对路径/`..`/链接、清单与实际成员一致、每项校验和匹配、敏感扫描无命中且目标仍唯一。

交付地址应绑定受理时确认的接收方类别和一次性/到期权限。下载、交付失败或接收方变更不得自动改投、转发、邮件群发或在聊天中粘贴链接。

## 6. 可观测性、指标与告警

首个完整观察窗口仅建立基线，不设成功率、时延或业务转化阈值；未采集字段必须写“无法判定”。所有分子、分母和排除原因必须可回放到 `export_id`，但运营周报只输出聚合结果。

```text
唯一定位通过率 = identity_verified 且唯一 api_key 的请求数 / 进入身份核验的请求数
导出生成成功率 = validated 的导出数 / started 的导出数
敏感拦截率     = 因敏感规则/路径越界而失败的导出数 / started 的导出数
交付完成率     = delivered 的导出数 / 已批准且已生成的导出数
按时清理率     = 在确认保留期内成功 expired_deleted 的包数 / 到期包数
```

按请求类型、数据类别、版本、失败分类和重试序号分组；不可按昵称、个人健康指标或未经批准的用户画像分组。另记录：候选账号数分布、重复昵称拦截数、审批拒绝/取消数、生成/校验/交付/清理阶段时延、大小区间、manifest 校验失败数、敏感扫描命中分类、权限拒绝、审计写入失败和下载次数。

立即阻断并升级的监控项：多候选仍进入生成、跨用户成员、Token/密码哈希/Cookie/密钥命中、审计写入失败、权限校验绕过、到期包未清理、完整性校验失败或同一 `export_id` 的不一致重放。不得将失败重试、敏感拦截或用户未下载自动解释为召回机会或发送触达。

## 7. 失败、重试与应急

失败须分类为：`identity_ambiguous`、`authorization_denied`、`approval_missing`、`scope_invalid`、`source_missing`、`allowlist_violation`、`sensitive_content_detected`、`integrity_check_failed`、`audit_write_failed`、`delivery_failed`、`cleanup_failed` 和 `internal_error`。错误返回应使用稳定分类和可操作的下一步，不回显路径、账号、密钥或内容。

可重试仅限暂态的读取、打包、交付或清理失败，且必须使用同一 `export_id`、同一已批准的范围和有界重试策略；每次都写审计。身份歧义、权限/审批缺失、allowlist 越界、敏感内容命中、完整性失败和审计失败均不可自动重试，必须停止并人工复核。已交付的包不自动重新发送；需重新交付时创建新的审批或明确记录已批准的重发。

发现疑似泄露、跨用户访问或凭据进入包时：立即停用导出入口和下载令牌，保全最小审计证据，不复制或扩散敏感包；通知安全/数据负责人和主 Agent，按既定事件响应评估撤销外部凭据、受影响范围和通知义务。运营不自行删除审计证据、不修改用户数据、不对外发送解释。

## 8. 上线检查与验收清单

1. 用两个相同昵称的受控账户验证：系统返回“需二次核验”，绝不选取任一账号或创建 TAR。
2. 用唯一且经授权的受控账户验证：仅在 `api_key` 锁定、审批有效、范围最小化后可生成；变更昵称不影响已锁定目标。
3. 覆盖全部角色：未授权、仅受理、仅审批、仅执行、紧急 break-glass；验证职责分离和审计完整性。
4. 对 allowlist、`../`、绝对路径、符号链接、其他用户目录、全局 `users/`、`backup/`、`tokens/`、`huawei-tokens/`、Cookie、配置和邀请码做负向测试，均必须失败关闭且无包留存。
5. 解包检查成员、manifest、SHA-256 和敏感扫描；确认用户资料不含邮箱、密码哈希、平台账号、`api_key` 或凭据，除非范围决策明确允许且另有批准。
6. 验证文件名、日志、指标和审计不含昵称、邮箱、完整/截断 `api_key`、文件路径、正文或密钥；验证可用 `export_id` 回放。
7. 回放读取/打包/交付/清理失败，以及重复请求、重试和服务重启；确认幂等、重试边界、到期删除与告警符合第 7 节。
8. 在生产等价权限与交付环境执行受控账户演练；记录版本、样本范围、原始分子/分母、失败分类和未验证项。任何上线阻断未通过即停止发布。

## 9. 必须由主 Agent 裁决

1. 导出入口是否仅支持本人自助访问，是否允许人工支持/迁移/取证，以及每类的法律依据与审批人；
2. 可导出的精确数据类别、`data.db`/记忆的字段级脱敏策略，以及任何 break-glass 凭据处理是否存在；
3. TAR 加密格式、密钥管理、交付渠道、下载次数和有效期；
4. 审计系统、日志访问边界、留存期限、删除机制和安全事件响应负责人；
5. 重试次数/退避、并发限额、文件大小上限、保留期和上线后的告警阈值（当前无数据基线）。

在这些决策完成并同步到产品与技术设计前，本文件只作为上线前约束，不能被解释为已上线承诺或可执行操作手册。
