# 报告主线与训练执行边界

- **日期**: 2026-08-07
- **类型**: product / architecture

## 背景与动机

产品讨论确认：训练能力需要依据目标、当前能力、运动习惯和恢复能力制定方案；报告则围绕运动记录复盘执行、表现、恢复、目标进程和下一阶段建议。报告是“观察—解释—决策建议”的主线，训练是把建议转成可确认、可执行方案的处方与执行模块。

## 方案选择

采用“产品主线统一、领域写入分离”的方案：

- 报告中心负责日报、周复盘和阶段建议，并固化事实截止时间、证据和 `Progression Decision`。
- 训练服务消费报告的结构化引用，生成调整提案、方案草稿或方案版本候选。
- 报告不能直接确认、启用或推进训练方案；训练只有在版本校验、安全校验和用户确认后才写入未来安排。
- `goal_intent` 显式区分 `completion`（完赛）和 `performance`（成绩突破），避免由是否填写目标成绩隐式推断。
- 运动习惯作为系统从活动、执行记录和反馈中推断的 `Athlete Habit Profile`，不增加独立手工画像表单。

没有采用合并报告与训练写模型的方案，因为这会让历史报告被未来方案反向修改，也会产生报告页静默写入训练的风险。

## 实现步骤

1. 更新 `CONTEXT.md` 的领域词汇，补充报告主线、运动习惯画像、目标意图和报告到训练的决策传递关系。
2. 更新报告产品方案，明确报告中心是产品主入口，并区分日报、周复盘和阶段建议的时间尺度。
3. 更新训练产品方案，明确训练是报告结论的处方与执行入口，保留用户确认和版本边界。
4. 更新训练系统与记忆系统设计，记录跨域结构化引用和写入职责。
5. 实现 `goal_intent` 的目标存储、训练建立向导和兼容旧目标推断。
6. 实现 `POST /api/training/proposals/from-report`、MCP 对应工具和报告到训练页的深链。
7. 补充服务层回归测试，确认报告衔接只产生 pending 提案，当前方案版本保持不变。
8. 追加 CHANGELOG，记录本次产品边界与运行时衔接变更。

## 遇到的问题与解决

现有设计机制已经存在“周复盘 → Progression Decision → 训练调整提案”的链路，冲突主要是页面主次叙事，而不是底层职责。实现时没有让报告自动写入方案，而是增加带报告/方案版本引用的 pending 提案入口，默认下周生效并继续复用现有确认接口，保留了报告不可写训练、训练确认后才生效的安全约束。
