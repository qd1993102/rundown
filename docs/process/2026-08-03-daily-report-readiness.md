# 日报生成前数据完整性门禁落地

- **日期**: 2026-08-03
- **类型**: feature / architecture

## 背景与动机

日报原先可以直接读取本地已有记录并生成，但“存在部分数据”不能证明目标日期及历史分析窗口已经
同步完整。活动、睡眠或负荷历史缺失时继续生成，会把未知状态误解为休息、低负荷或恢复良好。
Web、CLI 与 MCP 又有不同入口，只在页面加提示无法阻止其他调用方绕过。

## 方案选择

采用共享、无副作用的 `DailyReportReadinessService`，根据 Provider 能力和逐日同步完成证据输出
`ready / limited / blocked`。活动覆盖是硬门禁；辅助指标或历史窗口不足时，仅允许用户当次显式
选择受限版，并从确定性计算和 AI 输入中同时移除依赖章节。生成器必须接收不可变 readiness 快照，
从写入层阻止绕过。

同步和生成仍保持两个独立旅程。日报页只把目标日期传给同步页；同步页预填单日日期、切换对应月份、
锚定单日同步区域，并在返回日报时保留日期，不自动发起第三方同步。

## 实现步骤

1. 新增共享 readiness 模型、逐日覆盖事实查询和生成模式校验。
2. Web 新增预检接口和完整/受限/阻断交互，提交生成时在服务端二次校验。
3. CLI 与 MCP 共用同一门禁，提供机器可读的 `mode` 和结构化错误；`--skip-sync` 不再绕过检查。
4. 日报 Front Matter、详情与导出保存并展示覆盖快照、数据截止时间、最终性和省略章节。
5. 把同步成功、失败与进行中的逐日证据写入同步日历，区分已确认休息和未同步。
6. 增加报告日期到同步页的参数交接、月份定位、区域锚定和移动端布局验证。

## 遇到的问题与解决

- 旧同步日历只能说明活动可见性，不能证明所有健康维度完整：readiness 分维度判断，活动完成标记
  只作为核心事实和负荷窗口证据，健康数据单独检查。
- 历史不足与 Provider 不支持容易混淆：`unsupported` 不降低总体状态，`missing` 和
  `insufficient_history` 则进入受限版并明确省略结论。
- 睡眠占位值 `0` 可能被误算为有效趋势：只有正数睡眠时长或真实恢复指标才计入健康趋势覆盖。
- 页面预检可能在提交前过期：预检只控制交互，POST、CLI 和 MCP 在写入前均重新校验。
- 同步页日历异步加载导致首次锚点偏移：月份渲染完成后再次锚定，保证移动端目标卡片稳定出现在视口。

## 验证

- readiness 单元测试覆盖无标记活动、同步失败、Provider 不支持、受限版显式确认、28 天窗口、
  今日暂态、零值占位和写入层防绕过。
- Web 测试覆盖预检、HTTP 409、日期交接、月份定位、锚点和移动端结构。
- 完整测试结果见本次开发任务的验证记录；真实 Provider 补同步没有在本地验证中触发。
