# 交互式训练方案系统实现

- **日期**: 2026-07-31
- **类型**: feature

## 背景与动机

既有训练方案只隐藏在 `active-plan.md` 和日报快照中，用户无法稳定感知今日安排，也无法通过“反馈现实约束—查看差异—确认生效”持续迭代。本次实现以既有产品真相源和技术设计为边界，先交付可感知、可交互的闭环。

## 方案选择

- 继续使用用户隔离的 Markdown + YAML Front Matter，不引入新的数据库或任务系统。
- 新增统一 `TrainingService` 和 `TrainingRepository`，让 Web、MCP 与 Coach 工具共享状态迁移和安全规则。
- 方案采用不可变历史快照和 `active-plan.md` 实时读模型；反馈、提案与确认分文件保存。
- 第一版 Adjustment Engine 使用可回放的保守规则。疼痛只允许降级或暂停；在线 AI 后续只能贡献候选变更，不能绕过同一确认边界。
- 活动匹配第一版只做同日、去重、保守关联。同步未知和低证据都保持 `unmatched`，不写成跳过。
- Training Goal 继续使用 `goals/active/*.md` 作为唯一真相源；训练方案只保存 `goal_id` 和确认时快照。按用户决定不新增存量迁移，旧方案只读兼容。
- 无方案页面采用五步建立向导，向导状态留在浏览器；服务端只持久化共享目标和训练方案草稿。

## 实现步骤

1. 建立方案草稿、激活、自然周物化、旧 `active-plan.md` 迁移和私有原子写入。
2. 建立结构化反馈、调整差异、版本冲突、提案过期、拒绝和幂等批准。
3. 新增 `/training`，按“今日训练 → 本周安排 → 长期方案”展示，并提供四类快捷反馈。
4. 新增八个 Training API，并把六个 MCP/Coach 工具切换到两阶段写入。
5. 将主导航扩展为“训练 / 日报 / 同步 / 我的”，补齐 320px、键盘焦点和 `aria-live`。
6. 增加领域、Web、用户隔离、MCP 注册和兼容迁移测试。
7. 将无方案长表单改为目标选择、28 天基础确认、现实约束、草稿审阅和最终确认五步向导；目标快速创建复用“我的”相同仓库。

## 遇到的问题与解决

- 旧文件没有稳定 ID、版本或结构化周课次：迁移时只转换可以证明的字段，完整正文保存到 `legacy_notes`，写入 v1 历史后再替换实时读模型。
- 日报快照可能过期：训练页完全绕过 `plan_context`，直接读取训练服务。
- 无活动记录无法证明跳过：匹配层结合活动同步三态，缺少证据时使用 `unmatched`。
- 同时出现另一项文档改动：实现过程保留并行改动，不回滚或覆盖，仅追加本功能的独立文档条目。
- 旧目标表单和训练方案曾分别保存目标信息：新增 `TrainingGoalRepository` 统一读写，方案创建接口只接受 `goal_id`，从源目标生成历史快照。
- 活动为空不能说明没有训练基础：建立向导同时读取 28 天同步日历覆盖，覆盖不足时返回 `unknown` 并使用有明确说明的保守起始负荷。

## 2026-08-03 自适应启用与进程设计扩展

- **类型**: architecture

### 背景与动机

真实用户不会都在周一、训练前或草稿生成当天启用方案；近期跑量也可能因为旅行、数据缺口、疾病、伤病或主动恢复偏离其长期水平。现有实现把近期基础、长期能力、启用日期和日历周推进耦合，既会低估有稳定历史基础的运动者，也可能在单周超量后错误加速。

### 方案选择

- 保留 `Athlete Baseline` 作为单次训练相对强度参照，新增跨时间 `Athlete Capacity Profile`，避免一个概念同时承担训练识别和长期排课。
- 草稿启用前增加可失效 `Activation Preview`，确认后形成可改期或取消的 `Activation Schedule`，把确认时间、生效日期和首个完整训练周拆开；未来开始保持 scheduled，非周一开始使用不计阶段周的 Bridge Week。
- Training Scheme 继续定义策略和安全边界，新增 Progression State 表示实际走到哪里；完整周后形成不可变 Progression Decision。
- 正常 `advance` 在已确认边界内滚动 Weekly Plan；`accelerate`、阶段缩短和负荷区间变化继续形成待确认方案级提案。
- 历史能力只决定恢复上限和观察窗口，当前可持续能力决定安全起点；PB、峰值周量和单周超量都不能单独抬高负荷。

### 实现步骤

1. 版本化能力事实与 Athlete Capacity Profile 快照。
2. 启用预览、Activation Schedule、预览失效、开始日期、改期/取消、进入策略和 Bridge Week。
3. 扩展 ExecutionSummary 并建立 ProgressionDecisionEngine。
4. 接入 Skill 解释、方案级提案、Web 和 MCP。
5. 迁移旧方案并用周末启用、高基础快速恢复和单周负荷突增场景回放验收。

## 2026-08-03 实现记录

- `TrainingService` 新增能力档案读取和用户确认历史能力事实；近期已同步活动决定当前可持续周跑量，历史稳定能力仅作为推进/恢复参照。
- 草稿先生成不可变的启用预览，再以预览 ID 确认；预览同时固定草稿更新时间和事实截止时间，任一变化都要求重看建议。
- 启用支持今天、下个自然周和指定日期。未来开始保存为 `scheduled`，不会成为当天日报的执行依据；周中开始生成不计阶段推进的衔接周。
- 日报、Coach 与历史查询统一区分 `draft_available`、`scheduled_plan` 和 `no_effective_plan`，均不评价计划执行。
- 同步页保留来源与返回地址；训练来源回训练页刷新事实，日报来源回原报告日期重查完整性，未自动生成日报或改写训练方案。

当前只完成产品、领域和技术设计，未修改运行时代码或 README；实现需在本设计经用户确认后开始。

## 2026-08-03 报告中心边界实现

- `review_week()` 改为纯计算，避免训练页浏览行为写入 Progression Decision。
- 新增 `create_weekly_report()` 与 `reports/weekly/` 快照；同周只有用户显式生成时才刷新。
- 主导航统一为“训练 / 报告 / 同步 / 我的”；同步页移除日报列表，训练页移除周复盘写操作。
- 报告页提供训练深链和同步深链，调整批准、方案启用与推进仍限定在训练页。

## 2026-08-03 训练前说明与日报执行解释收口

- 训练前说明与日报不是同一类读模型：前者服务于即将开练的即时执行，使用本地恢复边界和课程内容生成简短指导，不再等待两个在线 Skill，也不把原始证据、负荷指标或 trace 发给浏览器。
- 日报增加只读的 `plan_execution_summary`：以报告日生效方案、活动覆盖三态和本地自然周跑步事实为输入，输出当天计划/实际、周目标、阶段、目标时间线和调整建议。同步未知保持待同步，跑步记录只证明有事实，不等同于完全匹配课次。
- 报告页面只能把建议深链到训练页；调整确认、方案改写和目标达成判断继续保留在训练或赛事事实流程中。

## 2026-08-03 训练、报告与同步的页面边界收口

- 报告中心不再把日报生成、周复盘、调整记录放在一张纵向页面。日报只管理单日状态和归档，周复盘只管理自然周，调整记录只管理提案索引。
- 当前自然周的请求返回不持久化 `weekly_checkpoint`，以 `not_final` 明确禁止进程决定；已结束周才写入正式 `weekly_report`。训练页的本周入口因此改为“查看本周进度”。
- 同步回跳保留 `tab`、日期或周范围：报告来源返回日报，训练来源返回训练。同步只补事实，报告只解释，训练页仍是唯一确认调整入口。
- 日报详情重排为结论、计划执行、训练事实和可展开依据；数据指标与 AI 观察仍可追溯，但不再干扰用户先理解行动。
